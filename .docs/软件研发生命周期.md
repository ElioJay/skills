# 软件研发生命周期

> 大纲版。目录结构定稿后按本大纲补全成详解文档，每个阶段写足目标、输入、活动、产出、评审、常见问题。

---

## 1. 概念

### 1.1 什么是生命周期

软件从"有一个想法"到"停止服务"的全过程。把它切成阶段，是为了让每一步都有明确的输入、产出和"做完了"的标准，让不同角色知道自己何时介入、交付什么。

### 1.2 阶段与活动

- **阶段**：按时间顺序排列的大段，回答一个核心问题（该不该做、做什么、怎么做、做出来、做对了吗、怎么上、上了之后、怎么下）。
- **活动**：阶段内的具体工作单元，各有产出物。目录结构里的二级目录就是活动。
- **贯穿活动**：不属于任何单一阶段、全程持续的工作：项目管理、配置管理、质量保证、变更管理、文档管理、安全合规。
- **AI 两组**：`00-AI开发` 是用 AI 做软件的规范、提示词、技能与评测，服务全部阶段；`90-AI系统` 是做的软件里有 AI 时多出来的过程。

### 1.3 过程模型只改组织方式，不改阶段本身

| 模型 | 怎么组织同一套阶段 | 适用 |
|---|---|---|
| 瀑布 | 顺序走一遍，阶段间有评审门 | 需求稳定、合规要求高 |
| V 模型 | 每个开发阶段与对应测试层级配对：需求对验收、设计对集成、编码对单测 | 强调可验证性 |
| 迭代与增量 | 多轮小瀑布，每轮交付可用增量 | 需求逐步明确 |
| 敏捷 | 需求到发布压缩进两到四周的迭代反复执行 | 需求多变、快速反馈 |
| DevOps | 发布与运维自动化成流水线，与开发并行 | 高频发布 |

### 1.4 参照的标准

| 标准 | 用在哪 |
|---|---|
| GB/T 8566-2022（等同 ISO/IEC/IEEE 12207:2017）软件生存周期过程 | 阶段与贯穿活动的过程口径 |
| GB/T 8567-2006 计算机软件文档编制规范 | 各活动产出文档的标准名 |
| GB/T 9385-2008 需求规格说明规范、GB/T 9386-2008 测试文档编制规范 | 需求规格与测试文档 |
| ISO/IEC 42001:2023 AI 管理体系 | `00-AI开发` 的使用约定、`90-AI系统` 的影响评估与透明信息 |
| ISO/IEC 5338:2023 AI 系统生存周期过程 | `90-AI系统` 的新增过程 |
| Agent Skills、MCP、AGENTS.md 开放规范 | `00-AI开发` 的技能、工具、指令文件 |

## 2. 八个阶段

每个阶段固定写以下小节：**目标 / 输入 / 核心活动 / 产出物 / 评审与出口条件 / 常见问题 / 目录落点**。

### 2.1 立项与可行性（`10-立项调研`）

- 目标：回答"该不该做"。
- 核心活动：明确业务目标、范围和收益；评估技术与资源可行性；定预算和里程碑。
- 产出物：目标与范围说明、可行性评估、预算与总体计划。
- 出口：立项评审通过。
- 常见问题：范围没定就开工，后面每个阶段都在补这个洞。

### 2.2 需求（`20-需求工程`）

- 目标：回答"做什么"。
- 核心活动：需求调研与获取、分析建模、编写规格、需求评审、建立基线，之后走变更管理。
- 产出物：原始需求、需求分析、需求规格与验收标准、评审记录、基线、变更单。
- 出口：评审通过并基线化，验收标准可测。
- 常见问题：只有原始需求没有规格，验收标准缺失导致测试无依据；变更不走流程。

### 2.3 设计（`30-系统设计`）

- 目标：回答"怎么做"。
- 核心活动：现状分析；概要设计（架构与技术选型、模块划分、接口契约）；详细设计（库表、类与接口、页面）；非功能设计；设计评审。
- 产出物：现状分析、技术方案、模块划分、接口文档、库表设计、详细设计、原型、非功能设计、评审记录与追溯矩阵。
- 出口：设计评审通过；库表、接口、页面与需求可追溯。
- 常见问题：不读既有代码直接设计，改坏既有功能；接口契约晚于实现，前后端口径不一致；非功能要求没人写，上线才发现慢和不安全。

### 2.4 开发（`40-开发实现`）

- 目标：回答"做出来"。
- 核心活动：编码、单元测试、代码评审、持续集成、静态检查。
- 产出物：源代码、单元测试、构建产物；文档侧放开发说明、示例代码、评审记录、扫描报告。
- 出口：评审通过、持续集成全绿、达到提测标准。
- 常见问题：评审流于形式；规范只在人脑里。

### 2.5 测试（`50-测试验证`）

- 目标：回答"做对了吗"。
- 核心活动：测试计划与用例、集成测试、系统测试、性能与安全测试、回归、用户验收。
- 产出物：测试计划、用例、测试数据、各级测试报告、缺陷统计、验收签字。
- 出口：缺陷收敛到准出标准，验收签字。
- 常见问题：没有用例只有"点一遍"；性能测试缺位，问题在生产才暴露。

### 2.6 发布与部署（`60-发布部署`）

- 目标：回答"怎么上"。
- 核心活动：版本冻结、发布评审、打包、升级脚本、灰度或全量部署、回滚预案。
- 产出物：冻结通知、发布说明、构建说明、升级脚本清单、部署手册、回滚预案。
- 出口：生产验证通过，回滚可执行。
- 常见问题：升级脚本顺序靠记忆；没有回滚方案。

### 2.7 运维与维护（`70-运行维护`）

- 目标：回答"上了之后"。
- 核心活动：监控告警、线上问题处理、缺陷修复、性能优化、小版本迭代。
- 产出物：监控告警说明、问题分析报告与证据原件、修复记录、优化方案、迭代计划。
- 出口：问题闭环；优化验收；或转入下一轮需求。
- 常见问题：问题修了不留根因；优化没有验收口径。

### 2.8 退役（`80-系统下线`）

- 目标：回答"怎么下"。
- 核心活动：数据迁移归档、系统下线、资料归档。
- 产出物：迁移方案、下线方案、归档清单。
- 出口：下线完成，数据与资料可追溯。

## 3. 贯穿全程的活动

不属于任何单一阶段，全程都在发生。本目录结构没有为它们设独立目录，产出物按它发生的阶段就近归档。

| 贯穿活动 | 做什么 | 产出物落点 |
|---|---|---|
| 项目管理 | 计划、进度、风险、沟通 | 计划在 `13-预算计划`，迭代排期在 `75-版本迭代` |
| 配置管理 | 版本、分支、环境、构建 | 基线在 `25-需求基线` 与 `61-版本冻结`，构建在 `44-持续集成` 与 `63-构建打包` |
| 质量保证 | 评审、审计、度量、合规 | `24-需求评审`、`39-设计评审`、`43-代码评审`、`45-静态检查`、`54-性能安全`、`62-发布评审` |
| 变更管理 | 需求与发布的变更控制 | `26-变更管理`、`61-版本冻结` |
| 文档管理 | 文档规范、模板、归档 | 各目录 README 与本文 |
| 安全合规 | 安全设计、安全测试、合规检查 | `38-性能安全`、`54-性能安全`、`45-静态检查` |

## 4. AI 两组

### 4.1 `00-AI开发`：用 AI 做软件

AI 不是某个阶段的产出物，而是每个阶段都在用的工具，所以单独成组、放在最前。四个活动：`01-协作规范` 定边界和用法，`02-提示词库` 与 `03-技能工具` 定能力，`04-评测记录` 验证能力是否可靠。提示词是一次对话的输入，技能是可按需加载、带脚本与参考文件的目录，反复使用且带流程的提示词升格为技能。

### 4.2 `90-AI系统`：做的软件里有 AI

项目本身要做模型功能时，在 8 个阶段之上多出来的过程：知识获取、数据工程、模型开发、模型评估、持续确认、影响评估、透明信息。不做 AI 功能的项目整组为空。

## 5. 阶段间的追溯

```
原始需求 ── 需求规格 ── 技术方案 ── 代码 ── 测试用例 ── 发布说明 ── 线上问题
   21         23          32       仓库       51          62          72
```

每份文档都应能指回上一环：技术方案带需求编号，测试用例对应验收标准，线上问题分析指回引入它的版本。目录结构里的需求编号前缀和日期前缀就是为了这条链。

## 6. 术语

| 术语 | 含义 |
|---|---|
| 基线 | 经评审确认、此后变更需走流程的版本 |
| 出口条件 | 阶段可以宣告结束的可验证标准 |
| 评审门 | 阶段之间的正式检查点 |
| 准出标准 | 测试阶段允许发布的缺陷阈值 |
| 回滚 | 发布失败时恢复到上一可用版本 |
| 追溯 | 从任一产出物找到它的上游依据 |
| 持续确认 | AI 系统上线后对模型效果的持续验证与漂移监控 |
