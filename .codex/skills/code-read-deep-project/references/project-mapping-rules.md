# 项目边界判定 · 模块发现与并行测绘 · 技术栈/构建拓扑 · C4 Context/Container · 模块间依赖(含环检测) · 跨模块路径走读（多语言）

> 供 `code-read-deep-project` 的阶段 1~8 使用。核心前提：分析对象是**一个项目/仓库（含多模块）**。
> 与模块级 `code-read-deep-module` 的差异：单位从"模块内文件"上升到"项目内模块/服务"，**重心是系统全景（C4 Context/Container）+ 模块间依赖 + 技术栈拓扑**，并靠**并行测绘**应对规模。

---

## 一、项目边界判定 + 多语言/多构建识别（阶段 1）—— 多语言

### 1.1 项目边界（本 skill 采用"整个仓库/代码库"为单位）
- 用户给的是一个**仓库根/项目根目录** → 项目 = 该根及其全部子树。
- 超大 monorepo 含多个**相互独立**的产品时 → 先做顶层 landscape 测绘，再请用户聚焦到其中一个产品/子树。
- 边界对外：项目子树之外（其它系统、第三方、外部服务）算"外部系统"，进 C4 Context。

### 1.2 多语言 / 多构建：识别技术栈与模块边界
项目常**多语言、多构建系统并存**（polyglot monorepo）。先扫描根与各子目录的构建/清单文件来识别：

| 生态 | 构建/清单文件 | 模块声明处 | 模块间依赖声明 |
|------|--------------|-----------|---------------|
| Java/Kotlin | `settings.gradle(.kts)` / 父 `pom.xml` | `include '...'` / `<modules>` | `project(':x')` / `<dependency>` |
| Maven 多模块 | 父 `pom.xml` `<modules>` | 各子 `pom.xml` | `<dependency>` 内部 groupId |
| JS/TS | 根 `package.json` `workspaces` / `pnpm-workspace.yaml` | 各包 `package.json` | `dependencies` 中的 `workspace:*` |
| Python | `pyproject.toml` / 多个包目录(`__init__.py`) | 子包 | `import` / 依赖声明 |
| Go | `go.mod`（可多模块）/ 顶层 `go.work` | 各 `package` 目录 | `import` 本仓库路径 |
| C#/.NET | `*.sln` | `<Project>` 引用 | `<ProjectReference>` |

> 多语言项目：**逐生态识别**，最终汇总出"语言分布 + 各模块所属生态"。

## 二、模块/服务发现 + 并行测绘（阶段 2）—— 项目级规模应对核心

项目太大无法逐文件读，业内做法是**广度优先建模块地图**：

### 2.1 发现模块/服务
- 优先读 **README / 架构文档 / 构建清单**（入口优先），据此列出顶层模块/服务/可部署单元。
- 用 Glob 印证目录结构；区分"业务模块 / 公共库 / 前端 / 基础设施(config、ci)"。

### 2.2 并行测绘（强烈建议）
- 模块较多时，**为每个模块派一个 Explore/子代理并行测绘**（各出"模块职责 + 对外门面 + 关键依赖"摘要），再在主代理汇总成模块清单与依赖图。
- 这样既覆盖全项目，又不让单一上下文爆炸。模块少（≤3~4）时可主代理内顺序测绘。
- 每个模块的测绘**止于摘要级**：要读透某个模块 → 委派 `code-read-deep-module`。

### 2.3 产出
模块/服务清单（每个一句话职责）→「模块/服务总览」段。

## 三、技术栈与构建拓扑（阶段 3）

- **技术栈清单**：语言分布、主要框架/中间件（Web 框架、ORM、消息、缓存）、构建工具。
- **构建拓扑**：从构建清单解析模块的**构建依赖图**（哪个模块 build 依赖哪个）。注意区分**构建期依赖** vs **运行期调用**（HTTP/RPC），二者可能不同。
- 产出 →「技术栈与构建拓扑」段。

---

## 四、系统上下文（阶段 4）→ ① C4 Context 图

C4 L1：把**整个系统当一个盒子**，画清：
- **使用者/角色**（用户、运营、定时触发者）。
- **外部系统**（第三方 API、支付/短信网关、外部数据源、其它团队的系统）。
- 系统与它们之间的关键交互（方向 + 用途）。
- 产出 → ① 系统上下文图（`flowchart`，外部系统/角色与本系统的边界）。

---

## 五、容器/模块架构（阶段 5）→ ② C4 Container 图

C4 L2：把系统拆成**可部署/可运行单元（container）**：前端应用、后端 API/服务、数据库、消息队列、缓存、定时任务等。
- 标注每个 container 的技术栈，以及它们之间的**运行期通信**（HTTP/RPC/MQ/共享库）。
- 多模块后端：可把各业务模块作为 container 内的组件，或独立 container（按是否独立部署）。
- 产出 → ② 容器/模块架构图（`flowchart`，标注通信协议）。

---

## 六、模块间依赖图 + 依赖健康（阶段 6）→ ③ 模块依赖图

项目级阅读的**结构重心**：

1. **构建模块间依赖图**：汇总各模块的内部依赖（构建期 `project(':x')` + 运行期调用），形成模块→模块有向图。
2. **依赖健康体检**（业内 ADP / 包原则，只体检不做架构评审）：
   - **模块间环检测**：有向环 → 标注「（模块循环依赖）」并记入「问题」（🟡/🔵）。
   - **分 tier / 分层破坏**：基础模块（如 `shared`）反向依赖业务模块 → 标注。
   - **稳定核心 / 易变边缘**：被依赖最多的模块是稳定核心（如 `shared`）。
3. 产出 → ③ 模块依赖图（环/破坏特殊标注）。

---

## 七、核心域、数据架构、入口与可部署单元（阶段 7）

- **核心域 / 限界上下文**：项目划成了哪几个业务域（order、payment…），各域核心数据与归属模块。
- **数据架构**：主要数据存储（DB/缓存/MQ）、跨模块共享的核心数据模型（如 `shared` 里的值对象）。
- **入口与可部署单元**：系统的"入口"（前端、对外 API/Controller、main、定时任务、消费者）与可部署单元清单。

---

## 八、关键端到端路径走读（阶段 8）—— 项目级"深度阀门"

项目巨大，**严禁逐模块/逐文件深挖**。只挑 **1~3 条最关键的跨模块端到端业务流**做中等深度走读。

- 例：前端下单 → `OrderController`（order）→ `OrderService` → `PaymentService`（payment）→ `shared.Money`。
- 走读**止于"跨模块路径级"**：每条路径只点出流经哪些模块/入口与外部 IO，不展开任一模块/文件/方法的内部实现。
- 每条路径附四级缩放委派：
  - 读某个**模块** → `code-read-deep-module <模块目录>`。
  - 读某个**文件** → `code-read-deep-file <文件路径>`。
  - 深挖某个**方法** → `code-read-deep-function <类名.方法名>`。

## 九、追踪过程的取舍原则

- **规模优先用并行**：模块多就派子代理并行测绘，避免单上下文超载；模块少则顺序读。
- **宁可标注，不可假装完整**：模块清单漏列、路径未走全、依赖未尽，都要显式声明边界。
- **广度优先 + 入口优先**：先 README/构建清单 → 模块地图 → C4 图 → 选择性走读；不要一头扎进某个模块。
- **构建期 ≠ 运行期**：依赖图要分清构建依赖与运行期调用，二者都画但标清。
- **不改代码**：全程只读不写，任何阶段都不编辑业务代码（符合仓库与全局规则）。
