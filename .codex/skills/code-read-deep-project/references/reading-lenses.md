# 阅读视角补充：测试 / 历史 / 运行期 / 框架（reading-lenses）

> 供 `code-read-deep-*` 家族按需加载。**静态读源码之外的四个补充视角**，能显著提升"读得准"。
> 粒度越大越值得用；按需取用，用了就在报告里注明证据来源。全程只读不改。

---

## 一、测试即规格（读测试理解意图）
- **何时用**：不确定"这段/这个东西应该做什么"、契约模糊、有现成测试时。
- **怎么用**：Glob 找对应测试（`*Test`/`test_*`/`*.spec.*`/`__tests__`），读用例名与断言——它们是**可执行的规格**；尤其看边界用例与异常用例，反推预期行为与契约。
- **产出补进**：方法级→「概念/算法」；文件/模块→「职责/对外接口」；项目→「核心域」。并在「问题」里对照"**测试声称的预期 vs 代码实际**"找背离。

## 二、git 历史 / 演进（为什么长这样）
- **何时用**：代码看着别扭/绕、想知道某段为何存在、判断稳定度与负责人时。
- **怎么用**：`git log --oneline -- <path>`、`git blame -L <a,b> <file>`、看改动热点（churn）与最近改动；读相关 commit message / PR 描述。
- **产出补进**：「定位/职责」补一句"演进背景"；「问题」区分"**刻意为之 vs 遗留债**"；项目级可识别活跃 vs 僵化模块。
- **注意**：只读历史不改；历史是线索不是结论。

## 三、动态 / 运行期证据（静态读会漏的）
- **何时用**：涉及反射、依赖注入装配、动态分发/多态、配置/注解驱动、插件机制——静态调用图会断的地方。
- **怎么用**：找 DI 装配点/配置文件/注解，确认"运行期到底连到哪个实现"；必要且允许时跑测试或读日志/调用链/trace 佐证；明确区分哪些是"**静态推断**"、哪些是"**运行期确证**"。
- **产出补进**：调用图/依赖图上对动态绑定边标注"（运行期绑定/反射）"；「问题」记录静态无法确定、需运行期验证的点。

## 四、框架感知（按框架约定解析）
- **何时用**：项目重度使用框架（Spring、Django/Flask、React/Vue、Express/Nest、gin 等）。
- **怎么用**：按框架约定解析**隐式行为**——
  - Spring：`@Autowired`/`@Bean` 装配、`@RequestMapping`/`@*Mapping` 路由、AOP 切面、事务注解；
  - Django/Flask：ORM 模型、中间件、`urls`/蓝图路由；
  - React/Vue：组件树、hooks/props 数据流、状态管理；
  - Express/Nest/gin：路由注册、中间件链、控制器。
  据此补全静态读看不到的"**框架替你接好的线**"。
- **产出补进**：入口识别（路由/装配点）、依赖图（DI 注入边）、组件/分层；项目级补进「技术栈/容器架构」。

---

## 五、原则
- 这些是**补充手段**，不喧宾夺主：主线仍是结构化阅读与出图；视角按需取用。
- 用了哪个视角，就在报告相应段落**注明证据来源**（测试 / 历史 / 运行期 / 框架约定）。
- 全程**只读不改**，符合家族一贯定位与仓库规则。
