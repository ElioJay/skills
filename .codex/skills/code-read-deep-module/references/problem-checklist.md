# 明显问题判定清单（仅逻辑 / 流程硬伤）

> 供 `code-read-deep-module` 的阶段 7（问题识别）使用。
> **范围严格限定**：只报"读代码时顺手可见的逻辑/流程硬伤"。
> 安全、性能、规范、架构等全维度质量问题**不在此范围**——那是 `code-review-deep-zh` 的职责。
> 注：本清单在 code-read-deep-* 家族内为**自包含副本**，修改判定标准须手动同步各 skill 的同名文件。

---

## 一、在范围内（应当记录）

### 空值 / None 安全
- 解引用可能为 null/nil/None/undefined 的返回值或字段，且无判空。
- 链式取值只判了头、没判中间（`a.getB().getC()` 中 `getB()` 可能为 null）。
- 空集合上取 first/last、空 Optional 直接 get。

### 异常与错误处理
- **空 catch**（吞异常，无日志无处理无重抛）。
- catch 过宽（`catch(Exception)` / `except:`）掩盖真实错误。
- 关键返回值/错误码被忽略（未检查 `delete()`、`err`、布尔失败值）。
- 错误路径上资源未释放（连接、文件、流、锁未 close/unlock）。
- `finally` 中 `return`/`throw` 吞掉了正在传播的异常。

### 控制流 / 流程
- **不可达死分支**，或守卫条件永远不可能成立。
- switch/match 缺 default 或新增枚举后不再穷尽，静默落空。
- 提前 return 跳过了必需的清理/收尾步骤。
- 循环边界差一（off-by-one）、循环变量更新错误。
- **无限循环 / 无限递归**（缺终止条件或终止条件不可达）。

### 并发 / 竞态
- 共享可变状态无同步、check-then-act（TOCTOU）。
- 锁顺序不一致的死锁可能、缺 await/缺 join。
- 迭代集合的同时修改它（ConcurrentModification 类问题）。

### 数据 / 状态
- 整数溢出、除零、浮点表示金额。
- 初始化顺序错误、异步后用了过期状态。
- DTO/实体转换漏字段、转换方向反了。
- 事务边界问题：按全局规则**事务只应在方法级**，发现类级事务或事务范围明显不当应记录。

### 模块级结构硬伤（本 skill 特有视角）
> 只报**明显、可指证**的结构问题，作为 🟡/🔵；不做架构好坏评判与重构建议（那是 `code-review-deep-zh`）。
- **依赖环 / 循环依赖**：模块内文件/子包形成有向环（违反 ADP），易致初始化顺序问题、难测试难复用。
- **分层破坏**：低层反向依赖高层（如 `dao`/`entity` 依赖 `web`/`controller`），破坏单向依赖。
- **门面被绕过**：消费方越过模块对外门面，直接依赖内部实现类（破坏封装边界）。
- **定义却从不被调用的写路径/状态流转**：如存在 `updateStatus` 却无人调用，导致状态永远停在初始值、写路径形同虚设。
- **跨文件契约误用**：模块内某文件对另一文件的契约误用（参数语义错、漏传必填、忽略返回值）。

## 二、不在范围内（不要记录，交给别的能力）

- 安全漏洞（注入、越权、密钥硬编码）→ `code-review-deep-zh`（安全维度）。
- 性能调优（N+1、无谓拷贝、算法可优化）→ `code-review-deep-zh`（性能维度）。
- 代码风格、命名、注释缺失、格式 → linter / `code-annotating`。
- 架构好坏评判、设计模式选型、重构建议 → `code-review-deep-zh`（架构维度）。
  （但**明显且可指证**的依赖环 / 分层破坏，可作为模块级结构提示记录，见「一 › 模块级结构硬伤」。）
- 编译器/类型检查器能直接报的错。
- diff 之外、与本入口链路无关的既有问题。

> 一句话边界：**「这段逻辑会不会跑出错」属于本 skill；「这段代码好不好/安不安全/快不快」不属于。**

## 三、分级标准

| 级别 | 含义 | 典型 |
|------|------|------|
| 🔴 阻断 | 会导致崩溃、数据错乱、死循环、明显跑错 | NPE、无限递归、吞异常致状态不一致、事务边界错致脏数据 |
| 🟡 建议 | 特定输入/边缘条件下出错或状态不一致 | 边缘空集合、漏判错误码、少数分支资源泄漏 |
| 🔵 提示 | 轻微隐患或健壮性欠缺，不紧急 | 防御性判空缺失但当前调用方保证非空、提示性边界 |

每条问题必须给：`file:line` + 证据（为什么是问题）+ 影响（不修会怎样）。

## 四、校准示例

### 应记录（真问题）
```java
String name = user.getProfile().getName(); // getProfile() 可能返回 null
```
→ 🔴 阻断，`UserService.java:42`：潜在 NPE，getProfile() 可能为 null，会导致请求 500。

```python
try:
    do_work()
except Exception:
    pass  # 吞掉所有异常
```
→ 🔴 阻断，`worker.py:88`：空 catch 吞异常，故障被静默掩盖，问题无法定位。

### 不记录（越界/误报）
```java
// 命名不够直观
int d = days(); // 变量名可优化
```
→ 不记录。这是风格问题，不在本 skill 范围。

```java
// 性能：列表里逐个查 DB
for (Long id : ids) repo.findById(id); // N+1
```
→ 不记录。性能问题交 `code-review-deep-zh`。

## 五、原则

- **少而准**：宁可少报几条确凿的，也不要堆砌可疑项。读代码时一眼可见、能给出证据的才记。
- **带证据**：每条都要能指到具体行并说清因果，不能"感觉有问题"。
- **不越界**：不确定是否属于本范围时，倾向不记录，并可在报告末尾一句话提示"如需完整质量审查请走 code-review-deep-zh"。
