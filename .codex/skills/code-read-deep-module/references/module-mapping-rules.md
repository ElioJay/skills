# 模块边界判定 · 结构总览 · 分层 · 依赖图(含环检测) · 外部依赖/消费方反查 · 入口与走读（多语言）

> 供 `code-read-deep-module` 的阶段 1~6 使用。核心前提：分析对象是**一个模块 = 一个目录/包子树**（含其子包）。
> 与文件级 `code-read-deep-file` 的差异：单位从"文件内构件"上升到"模块内文件/子包"，**依赖图与分层分析是重心**（业内 C4 Component / DSM / 包原则）。

---

## 一、模块边界判定 + 语言/构建系统识别（阶段 1）—— 多语言

### 1.1 模块边界（本 skill 采用"目录/包子树"为单位）
- 用户给的是一个**目录**（如 `src/order` 或 `com/example/order`）→ 模块 = 该目录及其所有子目录/子包。
- 用户给的是**包名/模块名**（如 `com.example.order`、`payments`）→ 先用 Glob 把它解析成目录子树。
- 边界对外的判定：**子树之内**算"模块内"，**子树之外**的引用算"外部依赖/消费方"。

### 1.2 多语言：边界线索 + 构建文件 + 依赖语法 + 典型入口
按语言/生态识别，决定"怎么找模块边界、怎么解析依赖、入口在哪"：

| 语言 | 模块边界线索 | 构建/清单文件 | 依赖/导入语法 | 典型入口 |
|------|-------------|--------------|--------------|---------|
| Java | 包目录 / Maven·Gradle module | `pom.xml`、`build.gradle` | `import a.b.C;` | `@RestController`/`@Service`、`public static void main` |
| Kotlin | 包目录 / Gradle module | `build.gradle.kts` | `import a.b.C` | 注解入口 + 顶层 `fun main` |
| C# | 命名空间目录 / 项目 | `*.csproj`、`*.sln` | `using A.B;` | `Controller`、`Program.Main` |
| Python | 含 `__init__.py` 的包目录 | `pyproject.toml`/`setup.py` | `import x` / `from . import y` | `__main__`、FastAPI/Flask 路由、`__init__.py` 导出 |
| JS/TS | 目录 / npm workspace 包 | `package.json` | `import ... from` / `require()` | `index.ts` 导出面、express/nest 路由 |
| Go | 包目录（同 `package`）/ go module | `go.mod` | `import ( ... )` | `func main`、`http.HandlerFunc` |

> 若模块根存在 `README` / `package-info.java` / `__init__.py` 文档 → **先读它**（业内入口优先阅读法）。

## 二、文件与子包清单（阶段 2）—— 模块"地图"核心

枚举模块子树内的文件与子包，形成「结构总览」，这是模块级阅读的地图（类比 file skill 的 Outline，但单位是文件/子包）。

### 2.1 要列的内容
- 目录树（到文件级，标注子包/分层目录如 `web/`、`dto/`、`entity/`、`service/`、`repository/`）。
- 每个**关键文件**一句话定位（它是什么角色：门面/服务/持久层/模型/适配器/工具）。
- 子包/分层目录的职责一句话。

### 2.2 原则
- **只列不展开**：本阶段不深读任一文件内部实现；想读某个文件 → 委派 `code-read-deep-file`。
- 大模块（文件很多）：按"分层目录"聚合列出，次要文件可合并成一行并标注"（其余 N 个 XX 类未逐一展开）"。

## 三、内部分层与组件协作（阶段 3）→ ① 组件/分层结构图

目标：看清模块**内部分了哪几层/几个组件、怎么协作**，找出主干。

1. **识别分层**：常见 `web/controller`（入口/门面）→ `service`（领域编排）→ `dao/repository`（持久层）→ `model/entity/dto`（数据），外加 `adapter/client`（外部适配）、`config`、`util`。
2. **识别组件协作**：哪个文件/类调用/持有哪个；门面经由哪些服务、服务经由哪些持久层实现主干。
3. **剪枝**：trivial（DTO getter/setter、纯工具）不进结构图；模块外的依赖留给阶段 5。
4. 产出 → ① 组件/分层结构图（`flowchart TD` 或 `classDiagram`）。

---

## 四、内部依赖图 + 依赖健康（阶段 4）→ ② 内部依赖图

模块阅读的**重心**：把模块内文件/子包之间的依赖画出来，并做健康体检（业内 DSM / Martin 包原则）。

### 4.1 构建内部依赖关系
- 解析模块内每个文件的 import/require/using，**只保留指向模块子树内**的依赖，形成 文件→文件（或 子包→子包）有向图。

### 4.2 依赖健康体检（只读体检，不做全维度架构评审）
- **环检测（ADP 无环依赖原则）**：用已访问栈检测有向环；发现环在图中用回边标注「（循环依赖）」，并在「问题」段记为 🟡/🔵。
- **分层破坏**：低层反向依赖高层（如 `dao` import 了 `web`、`entity` 依赖 `service`）→ 标注「（分层破坏）」。
- **稳定性提示（可选）**：被依赖多、依赖别人少的文件是"稳定核心"；反之是"易变边缘"。仅作提示。

### 4.3 产出
→ ② 内部依赖图（`flowchart LR`/`TD`，环与分层破坏特殊标注）。

---

## 五、外部依赖与消费方反查（阶段 5）→ ③ 上下文/依赖关系图

模块对外的 C4 Context 视角：

1. **外部依赖（上游）**：模块内 import 中**指向子树之外**的——其他内部模块、第三方库、外部系统（DB/HTTP/MQ/缓存/文件）。第三方标注"（第三方）"，外部 IO 单列。
2. **消费方（下游）**：全库 Grep 谁 import/引用本模块的**对外门面/导出符号**；框架反射/注解入口（路由/定时/监听）注明"由框架调用"；测试消费方单独标注。
3. 产出 → ③ 上下文/依赖关系图（`flowchart LR`：左侧消费方 → 本模块 → 右侧外部依赖/系统）。

- 找出模块的**核心领域类型/实体/状态机/数据模型**（业内"先找核心数据结构"上升到模块级）。
- 列出关键抽象（接口/门面/核心服务）与其语义，标 `file:line`。

## 七、入口识别与选择性走读（阶段 6 后半）—— 模块级"深度阀门"

模块文件众多，**严禁逐文件、逐方法深挖**（否则退化成对每个文件跑一遍 file skill）。

### 7.1 入口识别
按 1.2 的入口约定找模块入口点：对外门面、Controller/路由、`main`、DI 装配、导出 API。

### 7.2 选择性走读（1~3 条关键路径）
- 从入口出发，沿**最主要的 1~3 条端到端路径**做中等深度走读（路径经过哪几层、触达哪些外部 IO）。
- **止于"路径级"**：不在这里展开任一文件/方法的完整内部逻辑。每条路径附委派：
  - 想读某个**文件**整体 → `code-read-deep-file <文件路径>`。
  - 想深挖某个**方法**完整调用链/数据流 → `code-read-deep-function <类名.方法名>`。
- 形成 **模块 → 文件 → 方法** 三级缩放。

---

## 八、追踪过程的取舍原则

- **宁可标注，不可假装完整**：文件清单漏列、路径未走全、依赖未尽，都要显式声明边界。
- **广度优先 + 入口优先**：先铺模块地图与依赖图，再从入口选择性走读；不要一头扎进某个文件。
- **保持上下文连贯**：模块特别大时，可派 Explore 子代理分子包并行摸清结构再汇总。
- **不改代码**：全程只读不写，任何阶段都不编辑业务代码（符合仓库与全局规则）。
