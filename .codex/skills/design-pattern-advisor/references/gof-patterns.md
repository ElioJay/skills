# GoF 23 种设计模式速查

> **用法**：先过 YAGNI 闸门（"不加这个模式，现在的代码有什么实际问题？"），再用本表确认候选模式的适用边界。**"何时别用"列是重点**——它告诉你哪些情形是常见过度设计，以及更简单的替代方案。

---

## 创建型（5 种）

### Singleton 单例
- **意图**：保证一个类只有一个实例，并提供全局访问点。
- **何时用**：真正的全局共享状态（如配置中心、线程池、日志器），且多实例会引发错误。
- **何时别用**：只是想要"方便地全局访问"→ 用 DI 容器注入单实例；无状态工具类→ 用静态方法；测试需要替换实现→ 单例让 mock 极难，别用。
- **代价 / 坏味道**：全局状态隐式耦合；多线程懒初始化有坑；单例扩散后测试痛苦（隐藏依赖）。
- **频率**：中频（现代 DI 框架已承担大部分职责，直接写 Singleton 越来越少）

---

### Factory Method 工厂方法
- **意图**：定义创建对象的接口，由子类决定实例化哪个类。
- **何时用**：父类不知道要创建哪种子类，且希望子类有扩展入口；框架扩展点。
- **何时别用**：只有一种产品实现→ 直接 `new`；需要切换的产品只有有限几种且不会扩展→ 简单工厂函数或 `switch` 足够；强行引入只是为了"看起来规范"。
- **代价 / 坏味道**：每加一个产品就要加子类，类爆炸；如果产品种类稳定，继承体系是过度设计。
- **频率**：高频

---

### Abstract Factory 抽象工厂
- **意图**：提供一个接口，用于创建一系列相关或相互依赖的对象，无需指定具体类。
- **何时用**：需要确保同一"产品族"的对象配套使用（如 UI 换肤：按钮 + 输入框 + 滚动条同风格）。
- **何时别用**：产品族只有一个成员→ 退化为 Factory Method，别套抽象工厂；产品族数量和成员都可能变化→ 两个维度同时扩展会让接口频繁变动；只有两三种具体实现且不会增加→ 简单工厂或 DI 配置足够。
- **代价 / 坏味道**：新增产品族成员（横向扩展）时要改所有工厂接口，违反 OCP；接口膨胀。
- **频率**：中低频（跨平台 UI 框架、驱动层常见；业务代码少见）

---

### Builder 建造者
- **意图**：将复杂对象的构建过程与表示分离，同一构建过程可产生不同的表示。
- **何时用**：构造参数 > 4 个（尤其有大量可选参数）；对象需要多步骤装配且顺序有要求；同样的构建步骤要产生不同格式的输出（如导出 PDF/HTML）。
- **何时别用**：参数少于 4 个且都是必填→ 普通构造函数；只是想解决"可选参数混乱"→ 具名参数（Kotlin/Python）或 Options 结构体更简单；不需要多种输出格式→ 不必分离 Director。
- **代价 / 坏味道**：Builder 本身需要维护中间状态；若对象结构简单，引入 Builder 纯粹冗余代码。
- **频率**：高频（SQL/HTTP 请求/配置对象构建，链式 API 极常见）

---

### Prototype 原型
- **意图**：通过克隆现有对象来创建新对象，而不是通过类实例化。
- **何时用**：对象初始化代价昂贵（数据库查询、文件解析），且新对象与已有对象差异小；需要动态指定要创建的类（运行时注册原型）。
- **何时别用**：对象创建本来不贵→ 直接 `new`；对象有复杂引用图（深拷贝陷阱：循环引用、共享引用语义混乱）→ 序列化/反序列化或手动工厂更清晰；语言自带 copy/clone 已足够。
- **代价 / 坏味道**：深拷贝实现容易出 bug（漏掉某个字段、循环引用未处理）；每个类都要实现 `clone()`，侵入性强。
- **频率**：中低频

---

## 结构型（7 种）

### Adapter 适配器
- **意图**：将一个接口转换成客户端期望的另一个接口，使原本不兼容的类可以协作。
- **何时用**：集成第三方库/遗留接口，无法修改其源码；统一多个异构实现的调用接口。
- **何时别用**：可以直接修改源接口→ 改接口比包一层 Adapter 更干净；只是觉得类名不好听→ 不是 Adapter 的场景；过度包装导致接口比原始接口更复杂。
- **代价 / 坏味道**：多一层间接调用；适配器本身成为技术债，原始接口退役后要清理。
- **频率**：高频（系统集成、重构遗留代码场景极常见）

---

### Bridge 桥接
- **意图**：将抽象与实现分离，使二者可以独立变化。
- **何时用**：有两个独立变化的维度（如"形状 × 颜色渲染方式"），用继承会导致子类爆炸；需要在运行时切换实现。
- **何时别用**：只有一个变化维度→ 继承或策略足够；抽象和实现都很稳定不会独立变化→ 强行分离只增加间接层；团队不熟悉，引入后可读性反而下降。
- **代价 / 坏味道**：增加了抽象层次，代码跳转路径变长；两个维度如果耦合，分离后反而别扭。
- **频率**：中低频（GUI 框架、跨平台驱动常见；普通业务代码少见）

---

### Composite 组合
- **意图**：将对象组合成树形结构以表示"部分—整体"层次，使客户端对单个对象和组合对象的操作一致。
- **何时用**：数据本质是树形（文件系统、DOM、组织架构、菜单）；客户端需要统一处理叶节点和容器节点。
- **何时别用**：数据不是树形→ 强套 Composite 是过度设计；叶节点和容器节点操作差异很大，统一接口会产生大量空实现或异常。
- **代价 / 坏味道**：难以限制组合的深度/类型约束（子节点类型检查退化为运行时）；接口设计时叶节点的 `add/remove` 怎么处理需要妥协。
- **频率**：中频（UI 组件树、规则引擎、权限树等）

---

### Decorator 装饰器
- **意图**：动态地给对象添加职责，是继承的灵活替代方案。
- **何时用**：需要在不修改类的前提下叠加可选功能（如日志、缓存、权限校验、压缩加密）；功能组合是笛卡尔积，继承会爆炸。
- **何时别用**：只有一两个固定扩展点→ 直接继承或条件分支更简单；装饰器链过深导致调试困难（栈帧层层包裹）；行为需要跨装饰器协调→ 装饰器各自独立，协调逻辑放不进去。
- **代价 / 坏味道**：多层包装后 `instanceof` 失效；装饰器顺序有语义影响（顺序错了 bug 隐蔽）；对象标识（identity）可能被破坏。
- **频率**：高频（Java IO 流、Python `@decorator`、中间件管道）

---

### Facade 外观
- **意图**：为子系统提供一个统一的高层接口，降低子系统的使用复杂度。
- **何时用**：子系统复杂，调用方只需要有限几个入口；分层架构中隔离层间依赖（Service 对外暴露简化 API）。
- **何时别用**：子系统本来就简单→ Facade 是空壳；Facade 变成"上帝对象"承担了过多逻辑→ 应该拆分，不是加 Facade；调用方确实需要精细控制子系统→ 别封装掉灵活性。
- **代价 / 坏味道**：Facade 膨胀成上帝类；Facade 后的子系统被遗忘，成为黑盒难维护。
- **频率**：高频（SDK 封装、Service 层、API Gateway 都是 Facade 思想）

---

### Flyweight 享元
- **意图**：通过共享细粒度对象来支持大量对象，减少内存占用。
- **何时用**：系统中存在大量相似对象（数万+），且大部分状态可以外部化（内部状态共享，外部状态运行时传入）；内存是瓶颈。
- **何时别用**：对象数量少→ 共享带来的收益为零，复杂度纯属多余；内部状态无法与外部状态分离→ 享元不适用；现代硬件内存充裕，收益不覆盖引入成本。
- **代价 / 坏味道**：引入工厂/注册表管理共享对象；外部状态必须由调用方管理，接口变复杂；调试时对象不独立，难定位状态问题。
- **频率**：低频（游戏引擎粒子系统、字体字符缓存；普通业务代码几乎不用）

---

### Proxy 代理
- **意图**：为另一个对象提供代理，控制对该对象的访问。
- **何时用**：延迟初始化（虚代理）；远程对象访问（远程代理）；访问控制（保护代理）；AOP（日志、缓存、事务注入）。
- **何时别用**：直接访问目标对象没有问题→ 代理只增加间接层；用代理实现业务逻辑→ 应该放进 Service，代理只做横切关注点；代理链过深导致性能问题。
- **代价 / 坏味道**：动态代理（JDK/CGLIB）在调试时调用栈难看；代理与目标类接口必须一致，接口变更要同步。
- **频率**：高频（Spring AOP、ORM 懒加载、RPC Stub 全是代理）

---

## 行为型（11 种）

### Chain of Responsibility 责任链
- **意图**：将请求沿链传递，直到某个处理者处理它，解耦发送者与处理者。
- **何时用**：多个处理者都可能处理请求，且处理者在运行时动态组合（过滤器、校验链、审批流）；不想让发送者知道由谁处理。
- **何时别用**：处理者固定且顺序不变→ 顺序调用方法更清晰；请求必须被处理（链末尾无兜底→ 请求悄悄消失 bug）；链太长导致调试困难（要逐节点追踪）。
- **代价 / 坏味道**：请求可能不被任何处理者处理；链配置错误难发现；性能：遍历链有开销。
- **频率**：中频（Servlet Filter、Spring Security Filter Chain、审批流）

---

### Command 命令
- **意图**：将请求封装为对象，支持参数化、队列、撤销/重做。
- **何时用**：需要撤销/重做；需要请求队列或日志记录；需要将操作参数化传递（GUI 菜单/按钮）。
- **何时别用**：不需要撤销/队列/日志→ 直接调用方法；为每个操作都创建 Command 类→ 类爆炸（lambda/函数引用通常足够）；只是想解耦调用者→ 考虑观察者或回调。
- **代价 / 坏味道**：类数量爆炸（Java 8 前常见，lambda 后好很多）；撤销实现复杂（需维护历史状态）。
- **频率**：中频（现代语言 lambda 承担了大量 Command 职责）

---

### Interpreter 解释器
- **意图**：为语言定义文法的表示，并提供解释器来处理该文法。
- **何时用**：有明确定义的简单语言/规则需要解释（如正则、SQL、表达式求值、DSL）；文法稳定且相对简单。
- **何时别用**：文法复杂→ 用成熟的解析器生成工具（ANTLR/PEG）；文法频繁变化→ 每改一个规则要改大量类；性能要求高→ 解释器模式执行慢，用编译或虚拟机方案。
- **代价 / 坏味道**：文法规则多时类爆炸；维护成本高；性能差。
- **频率**：低频（专用 DSL 或规则引擎才用，普通业务极少）

---

### Iterator 迭代器
- **意图**：提供顺序访问集合元素的方法，而不暴露其内部表示。
- **何时用**：需要统一遍历接口（不同集合类型、自定义数据结构）；需要多种遍历方式（前序/中序/后序）。
- **何时别用**：语言/框架已内置迭代器（Java Iterable、Python `__iter__`、C# IEnumerable）→ 直接用，不要自己造；只是顺序访问数组→ `for` 循环足够。
- **代价 / 坏味道**：实现有状态迭代器需要维护游标，线程安全需额外处理；现代语言内置支持已覆盖 95% 场景。
- **频率**：中频（集合类内置，手动实现少见）

---

### Mediator 中介者
- **意图**：用中介者对象封装一系列对象的交互，使对象间不直接引用彼此。
- **何时用**：多个对象之间有复杂网状依赖（M×N 关系）；修改一个对象的行为影响多个其他对象（如聊天室、UI 组件协调、航空塔台）。
- **何时别用**：对象间交互本来简单→ 引入中介者是过度设计；中介者承载了太多业务逻辑→ 成为上帝类，比原始网状依赖更糟；事件/消息总线（MQ）能更松耦合地解决问题时，优先用总线。
- **代价 / 坏味道**：中介者自身极易膨胀成上帝类；调试时所有交互都绕过中介者，追踪难。
- **频率**：中低频（GUI 框架内部、工作流引擎；业务代码多用事件总线代替）

---

### Memento 备忘录
- **意图**：在不破坏封装的前提下捕获对象的内部状态，以便后续恢复。
- **何时用**：需要撤销/恢复（编辑器、游戏存档）；需要事务回滚。
- **何时别用**：状态很大（每次快照都是全量拷贝→ 内存爆炸）→ 用差量/日志重放；语言/框架自带序列化可以直接存档；对象状态变化极频繁→ 快照代价过高。
- **代价 / 坏味道**：快照存储开销大；如果原发器（Originator）内部结构变化，历史快照可能不兼容。
- **频率**：中低频（编辑器、版本控制场景；一般业务少见）

---

### Observer 观察者
- **意图**：定义对象间的一对多依赖，当一个对象状态变化时自动通知所有依赖者。
- **何时用**：事件驱动场景（用户操作、数据变更通知）；解耦发布者与订阅者；需要动态订阅/取消订阅。
- **何时别用**：依赖关系简单且固定→ 直接调用；观察者链导致"意外更新"难以追踪（A 改了 B，B 通知了 C，C 又触发 A）→ 循环依赖；调用顺序有严格要求→ 观察者通知顺序难保证；同步观察者链过长→ 考虑异步消息队列。
- **代价 / 坏味道**：内存泄漏（忘记取消注册）；通知风暴（一个变化引发连锁更新）；调试难（事件流难以静态追踪）。
- **频率**：高频（事件系统、响应式框架、MVC 中 Model 通知 View）

---

### State 状态
- **意图**：允许对象在其内部状态改变时改变自身行为，看起来像改变了类。
- **何时用**：对象行为随状态有显著差异（订单状态机、工作流）；大量 `if-else` 或 `switch` 按状态分支→ 状态模式消除分支。
- **何时别用**：状态少（2-3 个）且转换简单→ 枚举 + `switch` 更直接；状态和行为耦合不强→ 状态变量就够，不必封装成类；状态会频繁增加→ 每加一个状态就要加一个类，且要修改转换逻辑。
- **代价 / 坏味道**：类数量随状态数增加；状态转换逻辑分散在各状态类里，全局视图难。
- **频率**：中频（状态机、游戏角色状态、订单/审批流程）

---

### Strategy 策略
- **意图**：定义一系列算法，将其封装并可互换，使算法独立于使用它的客户端变化。
- **何时用**：同一行为有多种算法实现，需要运行时切换（排序策略、支付方式、路由算法）；消除基于类型的条件分支。
- **何时别用**：只有一种算法实现→ 接口 + 实现的结构是过度抽象；算法之间差异极小→ 参数化方法调用更简单；语言支持高阶函数→ 直接传 lambda，不必创建 Strategy 接口和实现类。
- **代价 / 坏味道**：客户端必须知道所有策略（才能选择）；策略类过多时同样有类爆炸问题。
- **频率**：高频（排序、校验器、定价规则、渲染器等）

---

### Template Method 模板方法
- **意图**：在基类中定义算法骨架，将某些步骤延迟到子类实现。
- **何时用**：多个子类有相同的算法流程，但个别步骤实现不同；控制反转（框架调用子类的钩子方法）。
- **何时别用**：步骤变化点多于固定步骤→ 骨架意义不大；需要在运行时动态组合步骤→ 策略模式更灵活；继承层次已经很深→ 再加一层模板方法让继承链更脆；现代语言可以用组合 + 函数参数替代继承骨架。
- **代价 / 坏味道**：继承强耦合（子类依赖基类实现细节）；基类改动会破坏所有子类；违反里氏替换时 bug 隐蔽。
- **频率**：高频（框架钩子、生命周期方法，但组合优于继承的思想正在取代它）

---

### Visitor 访问者
- **意图**：在不修改元素类的前提下，定义作用于元素类层次结构的新操作。
- **何时用**：类型层级稳定但需要频繁添加新操作（编译器 AST、文件系统统计）；需要对复杂对象结构进行多种不相关操作（打印、导出、校验）。
- **何时别用**：类型层级频繁增减→ 每加一个元素类要改所有 Visitor 接口及实现，维护成本爆炸；操作数量少（1-2 个）→ 直接在元素类里加方法；语言支持模式匹配（Rust、Kotlin、Scala）→ 密封类 + `when/match` 更简洁；访问者需要访问元素私有状态→ 破坏封装。
- **代价 / 坏味道**：双重分派理解成本高；元素类与访问者双向依赖；元素新增时 Visitor 接口的"开闭"失效。
- **频率**：低频（编译器/解释器工具链专属；业务代码几乎不用）
