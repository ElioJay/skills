# 🚀 分布式限流组件（rate-limiter）

## 一、组件概述

随着微服务架构的不断演进，系统面临的流量冲击日益复杂多变。为此，我们精心打造了这款
分布式限流组件，旨在为业务系统提供强有力的流量防护保障。

该组件不仅支持多种主流限流算法，而且提供了灵活丰富的配置能力，能够全面覆盖各类
业务场景，为系统的稳定运行保驾护航。

### 1.1 核心特性

- **高性能：** 基于 Redis + Lua 脚本实现，具备优异的吞吐能力，单节点可轻松应对
  高并发场景。
- **多算法：** 内置固定窗口、滑动窗口、令牌桶三种经典算法，充分满足不同业务的
  差异化诉求。
- **易接入：** 通过简洁优雅的注解方式即可完成接入，极大降低了业务方的接入成本。
- **可观测：** 内置完善的监控指标采集能力，便于实时掌握限流触发次数等关键指标。

### 1.2 适用场景

本组件广泛适用于接口防刷、秒杀削峰、第三方调用保护等诸多场景，是构筑系统稳定性
防线的重要一环。

## 二、快速开始

### 2.1 引入依赖

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>rate-limiter-spring-boot-starter</artifactId>
    <version>2.3.0</version>
</dependency>
```

### 2.2 完成配置

在使用之前，需要首先在 `application.yml` 中完成相关配置的设置工作：

```yaml
rate-limiter:
  enabled: true
  redis-key-prefix: "rl:"
  default-algorithm: SLIDING_WINDOW
```

### 2.3 开始使用

配置完成之后，即可通过在方法上添加 `@RateLimit` 注解的方式来实现限流能力的接入。

值得注意的是，在实际使用的过程中，建议根据业务的实际情况合理设置限流阈值，以避免
出现误限流等问题。

## 三、算法选型建议

不同的算法各有其适用的场景，需要辩证地看待和选择：

固定窗口算法实现简单、性能优异，但存在临界突刺的问题。滑动窗口算法有效地解决了
临界问题，同时也带来了一定的存储开销。令牌桶算法则能够很好地支持突发流量，为系统
提供了更加灵活的弹性空间。

综上所述，建议根据实际业务特点进行合理选择。

## 四、注意事项与展望

在使用过程中，需要注意 Redis 的可用性对组件的正常运行有着至关重要的影响。此外，
分布式环境下的时钟同步问题也需要引起足够的重视。

展望未来，我们将持续迭代优化该组件，不断丰富其功能特性，为业务的快速发展提供更加
坚实有力的技术支撑。✨
