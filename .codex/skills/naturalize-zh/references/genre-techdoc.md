# 规则卡 · 技术文档 / README / 技术博客

**最保守的一类，也是文体判不准时的默认口径。**

技术文档的读者是来查东西的，不是来读文章的。他们要的是准确、可检索、能照着做。任何为了「更像人写的」而牺牲准确性或可检索性的改动，在这一类里都是负收益。

同时它也是 AI 味最容易混进来的一类——因为宣传语（「强大」「灵活」「优异」）在技术文档里伪装成了技术描述。

---

## 一、口语化档位：**零**

不口语化。一个语气词都不加。

这里的目标不是「像人聊天」，是「像一个有经验的工程师在认真写文档」。那种文风本来就是简洁的书面语：短句、主动语态、少形容词。

**允许的**：把「在使用前，需要首先在配置文件中完成相关配置」改成「先在配置文件中完成配置」——这是简化，不是口语化。

**禁止的**：把它改成「配置一下就能用了，很简单」。

---

## 二、分段与结构：**几乎不动**

保留：

- 所有标题层级（`##` `###` 的层级关系不变）
- 所有列表（不把列表拉直成段落，也不把段落改成列表）
- 表格
- 代码块及其前后的说明位置关系
- 引用块 `>`
- 步骤编号

允许的结构改动只有两种：

1. **拆掉内联粗体标题**：`- **高性能：** 采用 Caffeine 实现` → `- 本地缓存基于 Caffeine 实现`
2. **合并纯铺垫段**：如果某段全是「随着…的发展」式铺垫，整段删掉（不是合并，是删）

---

## 三、标题：**只删套话前缀，不改语义**

技术文档的标题会被以下东西引用：

- Markdown 锚点链接（`[见缓存配置](#缓存配置)`）
- 站内目录 / 侧边栏
- 外部博客、issue、聊天记录里贴的深链
- 搜索引擎结果

改了语义就断链。所以这一类的标题处理是四类里最严的。

| 情况 | 处理 |
|------|------|
| `## 一、缓存模块概述` | **不动**。「一、」是编号，「概述」有实际含义 |
| `## 🚀 快速开始` | 只删 emoji → `## 快速开始` |
| `## 核心特性` | **不动**。「核心」在这里是分类词不是形容词 |
| `## 强大的扩展能力` | 删宣传词 → `## 扩展能力` |
| `## 总结与展望` | 如果整节是空转，标注 `[需补]` 或提请用户确认是否删除；**不要自作主张删标题** |

**判断标准**：改标题会不会让「这一节讲什么」变得不清楚？会就不改。

---

## 四、绝对不换的词

这是四类里最长的一份不动名单：

- **所有 API 名、类名、方法名、字段名**：`CacheLoader` `CacheManager` `getUserById` —— 大小写、驼峰、下划线全部原样
- **配置项、环境变量、命令行参数**：`spring.cache.type` `--max-heap` `NODE_ENV`
- **库名、框架名、协议名、产品名**：Caffeine、Redis、gRPC、Kubernetes
- **技术术语**：并发、幂等、熔断、限流、序列化、P99、QPS、TTL、CAS
- **版本号、错误码、状态码**
- **文件路径、URL、包名**

**同一个概念全文必须用同一个词。** 通用清单第 18 条（同义词循环）在这一类里是硬伤：文档里一会儿叫「缓存加载器」一会儿叫「CacheLoader」一会儿叫「加载组件」，读者会以为是三个东西。

改写时如果发现原文自己就在换着叫，**统一成出现次数最多的那个**，并在变更说明里指出来。

---

## 五、这一类特有的 AI 味高发点

按出现频率排序：

1. **内联粗体标题**——`- **高性能：** xxx`。这是技术文档里最明显的 AI 排版指纹，几乎必现。
2. **伪装成技术描述的宣传语**——「优异的读写性能」「完善的指标采集」「强大的扩展能力」「灵活适配各类业务场景」「无缝集成」。形容词删掉，只留事实。
3. **开头的「随着业务的不断发展」**——整段删。
4. **「旨在」「为此」「以便」**——「引入缓存模块，旨在有效降低数据库压力」→「缓存模块用于降低数据库压力」。
5. **「值得注意的是」「需要说明的是」**——直接说。
6. **「不仅…而且…」**——把一句话的两个特性拆成排比。改成并列或分成两句。
7. **系动词回避**——「该模块充当数据访问层」→「该模块是数据访问层」。
8. **「等」字滥用**——「监控缓存命中率等关键指标」。如果原文没说还有哪些指标，删掉「等关键指标」并标注 `[需补：还采集了哪些指标]`。
9. **「建议合理设置」类**——「建议合理设置缓存容量」等于没说。留标注问经验值。

## 六、示范

### 改前

```markdown
## 一、缓存模块概述

随着业务的不断发展，系统对数据访问性能的要求日益提高。为此，我们引入了缓存模块，
旨在有效降低数据库压力，提升整体响应速度。

缓存模块不仅提供了灵活的过期策略，而且支持多级缓存架构，为业务系统提供了强有力的
性能保障。

### 1.1 核心特性

- **高性能：** 采用 Caffeine 作为本地缓存实现，具备优异的读写性能。
- **易扩展：** 支持自定义 CacheLoader，能够灵活适配各类业务场景。
- **可观测：** 内置完善的指标采集能力，便于监控缓存命中率等关键指标。

### 1.2 使用方式

在使用前，需要首先在配置文件中完成相关配置，然后即可通过注入 `CacheManager` 的方式
来使用。

值得注意的是，在高并发场景下，建议合理设置缓存容量，以避免出现内存溢出等问题。
```

### 改后

```markdown
## 一、缓存模块概述

缓存模块用于降低数据库压力、提升响应速度。支持过期策略配置和多级缓存。

### 1.1 核心特性

- 本地缓存基于 Caffeine 实现。
- 支持自定义 `CacheLoader`。
- 内置指标采集，可监控缓存命中率。[需补：还采集了哪些指标]

### 1.2 使用方式

先在配置文件中完成配置，然后注入 `CacheManager` 使用。
[需补：配置项清单与最小可用示例]

高并发场景下需要合理设置缓存容量，否则可能内存溢出。[需补：容量设置的经验值或计算方式]
```

### 这组示范演示了什么

- **标题一个字没动**。`一、缓存模块概述` `1.1 核心特性` `1.2 使用方式` 都是有效锚点，全部保留。这一组恰好没有需要削的标题，正说明技术文档口径的保守程度。
- **口语化为零**。改后仍是标准技术书面语。
- **术语零改动**：Caffeine、CacheLoader、CacheManager 原样；`CacheLoader` 还补上了行内代码格式（这是排版修正，不是改词）。
- **列表结构保留**，只拆掉内联粗体标题。
- 删掉的宣传语：随着业务的不断发展 / 日益提高 / 旨在 / 有效 / 整体 / 不仅…而且… / 灵活的 / 强有力的性能保障 / 优异的 / 能够灵活适配各类业务场景 / 完善的 / 便于 / 关键指标 / 值得注意的是 / 建议合理 / 等问题
- **三处标注**，都锚在「原文做了主张但没给依据」的位置。

### 破功版对照（不要这样改）

```markdown
### 1.1 核心特性

- 本地缓存基于 Caffeine 实现，单机读性能可达 100 万 QPS。
- 支持自定义加载器，可以按需从数据库或远程服务拉数据。
- 内置指标采集，支持命中率、加载耗时、驱逐次数三类指标。
```

三处破功：

1. 「单机读性能可达 100 万 QPS」——**编造性能数据**。原文只说了「优异的读写性能」。
2. 「自定义加载器」——**把术语 `CacheLoader` 口语化掉了**，读者搜不到这个类。
3. 「命中率、加载耗时、驱逐次数三类指标」——**编造指标清单**。原文只提到命中率，剩下两个是猜的。

第 3 条尤其危险：它读起来完全合理（Caffeine 确实有这些指标），但文档写的是**这个项目采集了什么**，不是 Caffeine 支持什么。猜对了也是错，因为你没有依据。
