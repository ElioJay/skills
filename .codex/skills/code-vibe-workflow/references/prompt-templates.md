# 提示词模板速查（8 个核心动作）

本文件是 vibe-coding-workflow 的提示词配套，按需查阅、按场景填空。

---

## 0. 万能三段式（一切的起点）

**结构**：背景 → 任务 → 约束 & 期望

```
【背景】
{{我在做什么项目 / 当前文件的作用 / 相关技术栈}}

【任务】
{{要做的具体事情，越具体越好}}

【约束 & 期望】
- 必须复用现有的 {{模块/工具}}
- 不要引入新依赖
- 输出格式：{{完整文件 / 只给修改的部分 / Plan 方案}}
- 风格：{{遵循项目现有命名/缩进/注释习惯}}
```

**反例 vs 正例**：

```
❌ 帮我写个登录功能
✅ 【背景】SpringBoot 2.6.5 + MyBatis-Plus 项目，已有 User 实体和 UserMapper。
   【任务】实现 /api/login POST 接口，接收 {username, password}，校验后返回 JWT。
   【约束】
   - JWT 工具类已在 com.example.util.JwtUtil
   - 密码用 BCrypt 校验，参考 UserService.checkPassword
   - 失败统一抛 BusinessException(401, "...")
   - 输出：直接修改 LoginController.java，并补全测试
```

**进阶技巧**：
- Few-shot：给 1-2 个示例让 AI 模仿（写 DTO、写测试常用）
- 思考标签：复杂任务前加 "先在 `<thinking>` 中分析，再给最终代码"
- 强约束：用大写 / 加粗的 "禁止 XX"、"必须 XX"

## 1. 代码阅读

### 1.1 项目级理解
```
@CLAUDE.md @README.md @pom.xml (或 package.json)
帮我快速理解这个项目：
1. 它是做什么的？
2. 核心模块有哪些？分别在哪个目录？
3. 入口在哪？典型请求的调用链是怎样的？
4. 用了哪些不太常见的技术/模式？
请用「项目地图 + 调用链示意」格式输出。
```

### 1.2 单文件深度解读
```
@<file>
帮我逐方法讲解这个类：
- 每个方法做什么
- 调用了哪些外部依赖
- 潜在风险（性能、并发、异常处理）
- 如果要在这里加新方法，参考哪个现有方法写法
```

### 1.3 调用链追溯
```
查一下 `<ClassName>.<methodName>` 这个方法：
- 在哪些地方被调用？
- 每次调用的上下文（什么场景下会触发）
- 如果改它的签名，会影响哪些文件
```

**实战技巧**：让 AI 画 ASCII 调用链图，比纯文字更易理解。

## 2. 新功能开发（Plan → Confirm → Code → Test）

### 2.1 Plan 阶段
```
我要新增功能：{{功能描述}}

约束：
- 复用现有的 {{已有模块}}
- 不引入新依赖
- 数据库 schema 变化最小

请先：
1. 探索相关代码，理解现状
2. 给出 2-3 种实现方案，列出优缺点
3. 推荐其中一种
4. 列出要新建/修改的文件清单
```

### 2.2 编码阶段
```
按方案 X 实现，注意：
- 每改一个文件后简要说明改了什么
- 实现完不要急着跑测试，等我看一眼
```

### 2.3 测试阶段
```
为新增功能写单元测试，要求：
- 覆盖正常路径 + 至少 2 个边界场景
- 用项目现有测试框架
- 跑一遍测试，失败的话自己修复
```

## 3. Debug

### 3.1 通用 Bug 报告
```
【现象】
{{具体的错误现象，截图、日志、报错栈贴全}}

【期望】
{{应该是什么样}}

【复现步骤】
1. ...
2. ...
3. 出现 {{错误}}

【已尝试】
- {{尝试过什么、结论是什么}}
- {{排除了什么可能性}}

【相关文件】
@src/xxx/Yyy
@src/xxx/Zzz

【任务】
帮我定位根因（不要急着改代码），列出可能的 3 个原因，
按可能性排序，告诉我每个原因怎么验证。
```

### 3.2 加日志辅助定位
```
我不确定问题出在哪一步，帮我在以下位置加 log（用项目的 SLF4J/console）：
1. 入口参数
2. 关键分支
3. 外部调用前后
跑一遍后我把日志贴回来。
```

### 3.3 最小复现用例
```
帮我写一个最小复现用例（单元测试形式），
能稳定复现这个 bug。然后我们再分析。
```

**Debug 黄金法则**：
1. 先定位，再修复（让 AI 列原因，别让它直接改）
2. 不要相信第一个答案 —— 用 Codex 独立判断一次
3. git bisect 思路：能复现 commit + 不能复现 commit，让 AI 找差异

## 4. 重构

### 4.1 提取重复代码
```
@<file1> @<file2>
这两个类里都有 {{XX 逻辑}}，几乎一样。
帮我抽取成一个 {{ToolName}} 工具类。
要求：
- 不改变两个 Service 的对外行为
- 抽取后跑一遍现有测试，确保通过
- 给工具类加上单元测试
```

### 4.2 模式重构（换框架）
```
把 src/<dir> 下所有 {{旧写法}} 改成 {{新写法}}。
要求：
- 一次改一个文件
- 每改完跑对应测试
- 全部改完后给我一个改动清单
```

### 4.3 性能重构
```
@<file> 的 {{methodName}} 方法太慢（{{当前耗时}}）。
分析瓶颈，给出 2-3 个优化方向（先不要改代码）。
重点考虑：
- N+1 查询
- 流式处理代替全量加载
- 缓存
```

**重构三原则**：
1. 必须有测试兜底（重构前先补测试）
2. 小步前进（一次一个点，跑测试，commit）
3. 保留行为（强调"不改变外部行为"）

## 5. 写测试

### 5.1 单元测试模板
```
@<file>
为这个工具类写完整单元测试：
- 用 {{JUnit 5 / pytest / Jest...}}
- 覆盖：正常用例、null、空字符串、非法格式、边界值
- 用 @ParameterizedTest（或 pytest.mark.parametrize）减少重复
- 命名风格：{{methodName_scene_expected}}
- 写完后跑 {{mvn test / pytest / npm test}} 确认通过
```

### 5.2 测试驱动 AI 编程
```
1. 先写测试（描述需求 → 生成测试用例）
2. 你 review 测试是否表达了意图
3. 让 AI 写实现，目标：跑通测试
```

这种方式能极大降低 "AI 写跑偏" 的概率。

## 6. 写文档 / 注释

### 6.1 函数注释（项目风格）
```
@<file>
为公共方法补 {{JavaDoc / docstring / TSDoc}}，要求：
- 风格参考 @<reference-file>（已有注释作为示范）
- 只写 WHY 和约束，不写 WHAT（方法名已自解释）
- 包含 @throws / Raises 的真实抛出场景
```

### 6.2 生成 README
```
@<config files> @<entry files>
帮我生成 README.md，包含：
- 项目简介（一句话）
- 技术栈
- 本地启动步骤
- 主要 API（从 Controller/Router 反推）
- 目录结构
风格简洁，不要营销语言。
```

### 6.3 API 文档
```
@src/controller/** (或 routes/**)
为所有接口生成文档（Markdown 表格）：
| 方法 | 路径 | 入参 | 出参 | 说明 |
```

## 7. Code Review

### 7.1 自 Review 维度评分
```
review 当前所有改动（git diff），按维度打分（1-5）并给出具体问题：

| 维度 | 分数 | 问题 |
|------|------|------|
| 正确性 | x | ... |
| 可读性 | x | ... |
| 性能 | x | ... |
| 安全 | x | ... |
| 测试覆盖 | x | ... |

最后给出 Top 3 必须修复的问题。
```

### 7.2 切到 Codex 做第二意见
```
codex
> review 当前 git diff，重点关注：
> - 安全漏洞（SQL 注入、XSS、敏感信息）
> - 性能问题（N+1、死循环、大对象）
> - 异常处理是否完整
> - 是否有未覆盖的边界场景
```

详细 Review 清单见 `review-checklist.md`。

## 8. 提交 / PR（CLAUDE.md 规则版）

```
1. git status / git diff / git log -5  并行查看（理解改动 + 学习提交风格）
2. 输出："拟提交文件 + commit message（英文，匹配项目风格）"
3. 等用户回 "go" 或 "ok"
4. git add <specific files>（不用 -A）
5. git commit -m "<message>"
6. git status 验证

注意：用当前分支，不新建分支；不主动 push，不主动建 PR。
```

**commit message 示例**：
- `feat(login-stats): add 7-day login count API`
- `fix(order): handle null tax amount in calculator`
- `refactor(repository): migrate JdbcTemplate to MyBatis-Plus`
