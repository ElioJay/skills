# 缺陷分级与范围锁定

分级决定**什么时候修**，范围锁定决定**这次修到哪为止**。两件事都不做，修复就会在"先修哪个"和"顺手都改了"之间失控。

## 1. 分级维度

按五个维度看，任何一个维度拉到顶都会把优先级顶上去：

| 维度 | 要问的问题 | 拉高优先级的信号 |
|---|---|---|
| **影响面** | 多少用户 / 多少租户 / 多少下游系统受影响？ | 全量用户、关键客户、影响多个下游 |
| **严重度** | 坏了以后用户损失什么？ | 数据错误、资金错误、不可逆操作、安全问题 |
| **紧急度** | 现在正在发生，还是特定条件下才会？ | 正在持续发生、且随时间恶化 |
| **是否阻塞主流程** | 主流程能不能继续走下去？ | 主流程完全走不通，没有可用绕行 |
| **有无数据错误** | 是否产生错误数据或错误状态？ | 已经写入错误数据、需要对账或修复存量 |

补充维度（用于同级别内排序）：有无绕行方案、复现概率、影响是否随时间累积、是否对外可见（客户投诉 / 监管口径）。

### 分级的常见偏差

- **只看复现概率**：低频但会造成数据错误的缺陷，比高频但只影响展示的缺陷更该先修。
- **只看用户数**：一个只有 1 个用户、但那是最大客户的缺陷，影响面其实很大。
- **把"难修"当成"不急"**：难度不参与分级，只参与排期。
- **把"已经有人在抱怨"当成最高级**：要按维度复核，投诉量不等于严重度。

## 2. 分级后的处理优先级

本仓不强制一套数字等级，但**必须给出可排序的结论并写理由**。可用的口径：

| 优先级 | 判据 | 处理节奏 |
|---|---|---|
| 立即处理 | 正在发生 + 影响主流程或产生数据错误 | 当下就修，先考虑止血（必要时转 `incident-response`） |
| 本次迭代必修 | 影响面明确、有绕行方案但绕行成本高 | 排进当前迭代，锁定范围后修复 |
| 计划修复 | 影响面小或有可用绕行 | 排入后续迭代，写清接受现状的理由 |
| 记录不修 | 极低影响、修复成本远高于收益 | 记录在案并写明不修的理由，便于日后回看 |

**"不修"也是要写理由的决定**，不是默认状态。写下理由可以避免同一件事被反复提。

## 3. 把模糊描述收敛成可复现条件

"偶尔会报错""有时候数据不对"不能直接进入修复。用下面的清单逐项问清，直到能在自己的环境里把缺陷稳定或按概率复现出来：

1. **入口**：从哪个界面 / 接口 / 命令 / 任务开始？用户角色与权限是什么？
2. **前置条件**：环境（版本、配置、开关、依赖服务）、数据状态（哪些记录、什么状态、数据量级）、时间点（是否与批处理、月度结算、发布窗口相关）。
3. **操作序列**：一步一步做了什么？是否有并发或多人同时操作？
4. **期望结果与实际结果**：分别是什么？差异具体在哪个字段 / 哪个状态 / 哪个数值？
5. **发生频率与范围**：每次必现还是偶发？偶发的概率大概多少？影响全部数据还是特定数据？
6. **证据**：报错文本与堆栈、`traceId`、相关日志片段、截图、涉及的记录 ID。
7. **绕行**：用户现在怎么绕过它？绕行是否改变了数据？

收敛结果要写成**别人能照着复现的步骤**。写不成步骤，说明理解还不够，继续问，不要开始改代码。

**偶发缺陷**：不能稳定复现时，记录触发条件的相关性（时段、并发度、数据规模、特定输入），先把它变成"在 X 条件下 N 次里出现 M 次"，再动手。无法收敛时按"未复现"路径处理，不要靠猜改代码。

## 4. 区分缺陷、需求变更与误报

先分类再动手，三类东西的处理方式完全不同：

| 类型 | 判据 | 处理方式 |
|---|---|---|
| **缺陷** | 行为与**已确认的**需求、文档、接口契约、既有测试或用户合理预期不符 | 走本 skill 的修复闭环 |
| **需求变更** | 原行为符合当时约定，是期望变了（新规则、新口径、新交互） | 不走缺陷流程：先改需求与验收标准，再作为变更实现；不要在缺陷单里偷偷改行为 |
| **误报 / 非缺陷** | 环境问题、数据被人为改坏、用户操作错误、重复提交、第三方故障、文档本身写错 | 说明判定依据并关闭，把结论写进记录 |

判定陷阱：

- **拿"现有实现"当需求**：实现和文档不一致时，要问清哪个是约定，不能默认实现即正确（否则任何不一致都会被当成"需求变更"推掉）。
- **拿"现有测试"当需求**：测试本身可能写错了。测试与需求冲突时要指出冲突并让用户裁决，而不是两边的行为各改一半。
- **口径模糊就动手**：需求没写清的地方，先确认期望行为（期望是什么、边界在哪），再决定改代码还是改需求。

## 5. 范围锁定与"先问再扩"的判据

### 锁定

修复开始前写清两句话：

- **本次修什么**：一句话描述目标行为的变化。
- **本次不修什么**：明确列出看到但这次不动的问题（相邻代码的坏味道、偶然发现的另一个边界问题、可以优化的性能点）。

写下"不修什么"是本流程的关键动作——它把"顺手改一下"从习惯变成需要显式决策的事。

### 什么时候必须先问

出现下面任一情况，停下来向用户确认，不要自行扩大范围：

- 最小改动做不到，必须改动**公共接口、共享工具、数据结构或对外行为**。
- 修复需要改**数据库结构、存量数据或迁移脚本**。
- 修复会改变**其他调用方的行为**或需要同步修改多个服务。
- 缺陷的成因指向**更上层的设计问题**，改一处会牵出连锁修改。
- 修复需要**升级依赖、调整框架版本或改构建配置**。
- 修复需要**改动或新增测试之外的东西**（例如改 CI 配置、改告警规则）。
- 缺陷本身说不清是缺陷还是需求变更（见上一节）。

确认时给出三样东西：**为什么必须扩**、**扩了影响哪些代码与调用方**、**需要补哪些回归**。让用户能做决定，而不是只问一句"能扩大范围吗"。

### 允许的顺带动作

只有一类顺带改动是允许的：**为验证缺陷所必需的测试与复现脚手架**（失败测试、最小复现脚本、必要的测试数据构造）。它们不改变生产行为。除此之外的改动都按扩大范围处理。
