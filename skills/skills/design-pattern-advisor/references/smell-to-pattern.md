# 坏味道 → 候选模式 对照表

> **怎么读这张表**：先回到 SKILL.md **第 0 步 YAGNI 闸门**——确认"变化/重复**真实出现过 ≥2~3 次**"（不是你猜它会变），再用本表从**症状**定位候选模式。
> 一个症状常对应**多个候选**，必须结合「适用边界 / 代价 / 最简替代」三列权衡，不要看到症状就套模式。
> **默认倾向：不用模式**。模式是用复杂度换扩展性，只有当扩展性收益已经兑现（变化已发生、还会再发生）时才划算。拿不准时，先写"最简替代"列里的方案。

---

## 主表：症状 → 候选模式 → 边界 / 代价 / 替代

| 症状 / 坏味道 | 候选模式 | 适用边界（满足什么条件才值得上） | 代价 / 风险 | 不用模式的最简替代 |
|---|---|---|---|---|
| 按"类型/枚举"分支的 if/switch 且分支会增长，每种行为不同 | Strategy | 同一处分支已出现 ≥3 个分支、且**还会新增类型**；各分支逻辑互不依赖、可独立测试 | 类数量膨胀；要管理策略的注册/选择；简单分支硬套反而绕 | `Map<类型, 处理函数>`（或函数指针/字典）做路由表，新增类型只加一行 |
| 对象在不同"状态"下行为不同且状态间会转移 | State | 状态 ≥3 个、转移规则复杂、**散落的 if (status==X) 已开始打架**；非法转移需要拦截 | 状态类爆炸；转移图要单独维护；状态少时过度设计 | 一张**状态转移表** `{当前态: {事件: 下一态}}` + 集中校验，少量状态用枚举 + switch |
| 创建逻辑复杂/分散/运行时才知道具体类 | Factory Method / Abstract Factory / Simple Factory | 创建步骤多/有分支、调用方不应感知具体类；**Abstract Factory** 仅当要成套创建"产品族"且族会增加 | 多一层间接；Abstract Factory 加产品维度时要改所有工厂，很重 | 一个静态工厂方法 / 构造函数；只有一种实现时**直接 new** |
| 构造参数很多、可选组合多、易传错位 | Builder | 必填+可选参数总数多（如 >4）、组合多、存在"参数顺序易错/同类型相邻"；需要构造期校验或不可变对象 | 模板代码多；参数少时啰嗦 | **重载构造函数** / **默认参数** / 具名参数（kwargs、命名实参）；少量可选项用参数对象 |
| 想给对象动态叠加职责（日志/缓存/校验）又不想改它/不想继承爆炸 | Decorator | 职责可**自由组合、运行时叠加**、顺序有意义；继承会产生组合爆炸（N 种职责→2^N 子类） | 小对象层层包裹，调试栈深、难读；职责固定时不值 | 固定职责直接内联；横切关注点用**中间件/拦截器/AOP**链；包一个薄封装类 |
| 接口不兼容，要适配第三方/老接口/不同数据形状 | Adapter | 无法改动对方接口（第三方/遗留），且**多处**要用这个目标接口；适配逻辑稳定 | 多一层映射要维护；对方接口变了要跟着改 | 一个**转换函数 / 映射方法**（DTO ↔ 领域对象）；只用一处就别建类 |
| 一个变化要通知多个互不相关的对象 | Observer / 发布订阅 | 订阅者数量/种类**不固定、会增减**，发布方不该知道订阅方；松耦合收益明确 | 调用链变隐式、难追踪；忘了退订→内存泄漏；异步时序/异常难控 | 发布方持有一个**回调列表**逐个调用；订阅方少且固定时**直接方法调用** |
| 一系列步骤骨架固定、只有个别步骤因场景而变 | Template Method | 算法骨架稳定、步骤顺序不变、**只有 1~2 个步骤要变体**、变体间共享大量流程 | 继承耦合强、不灵活；子类被父类流程绑死；多变化点时僵硬 | **高阶函数 / 回调**把可变步骤当参数传入（组合优于继承） |
| 请求要在多个处理者间依次传递直到被处理 | Chain of Responsibility | 处理者**动态可增减/可重排**、谁处理在运行时定、可能没人处理；链条逻辑解耦有收益 | 调试要追整条链；可能无人处理被吞掉；性能（逐个试） | 一个**有序处理器列表** + 循环，命中即返回；固定顺序写顺序 if 即可 |
| 请求要可排队/可撤销/可记录/可重放 | Command | 真的需要 **undo/redo、排队、事务化、审计回放、延迟执行**之一 | 每个操作都要建命令对象，样板多；只为"调用一下"则过度 | 直接调方法；要 undo 先存"逆操作"或快照，别一上来就 Command |
| 复杂子系统要给外部一个简单统一入口 | Facade | 子系统调用步骤多/顺序固定、被多处复用、想隔离内部变化与外部依赖 | 易长成"上帝类"；可能掩盖本该简化的内部设计 | 抽一个**门面函数 / 服务方法**封装调用序列；一处用就内联 |
| 跨层传输数据 / 想解耦业务与持久层 | DTO + Repository | 领域模型与传输/存储模型**已经分化**、要防止数据库结构泄漏到业务层、需要切换/Mock 存储 | 模型映射样板多（领域↔DTO↔实体）；小项目纯增负担 | 直接用领域对象传输；DAO 足够时不引入完整 Repository 抽象 |
| 业务查询条件要可组合、可复用 | Specification | 过滤规则**多、要 AND/OR/NOT 自由组合、跨处复用**、需把业务规则显式命名 | 规格类增多；简单查询绕远路；与 ORM 拼接有成本 | 查询条件传**谓词函数**（predicate / lambda）；固定查询写具名查询方法 |
| 到处是 `if (x == null)` 防御判断 | Null Object | "空"有**明确的默认行为**、调用点多、想消灭散落的空判断；空对象语义不误导 | 多一个空实现类；空对象掩盖"本该报错"的情况→隐藏 bug | 入口处兜底默认值（`x ?? 默认`）；集合**返回空集合不返回 null**；该报错就报错 |
| 依赖难替换、不好做单测 | 依赖注入 (DI) | 依赖有**多实现/要 Mock**、对象组装与使用要分离、生命周期需统一管理 | 配置/容器复杂度；过度注入导致到处接口、可读性差 | **构造函数显式传依赖**（手工注入即可，不必上容器/框架） |

---

## 怎么用这张表

1. **没过 YAGNI 闸门就别查表。** 只有一处分支、只有一种实现、变化还没发生第二次——直接写最直白的代码。模式是对"已确认的变化"的回应，不是对"想象的变化"的投保。

2. **一个症状对多个候选时，选代价最小、最贴合"真实变化方向"的那个。** 先问"实际在变的是哪一维"（是行为在变→Strategy，还是状态在转→State，还是创建在变→Factory），按真实变化轴选，别按名字顺手挑。

3. **拿不准就先写"最简替代"列。** 函数表、回调、默认参数、谓词、空集合这些零成本方案先顶上；**等第二次变化真的出现**，重构到模式的成本远低于一开始就过度设计后再拆掉的成本。

4. **区分"现在就值得"和"将来也许"。** 只为**已经发生且还会再发生**的变化上模式；"将来可能要支持 XX"属于 YAGNI，记个 TODO 即可，不要现在就为它加抽象。

5. **模式可组合，但一次只解决一个症状。** 别为了"用上模式"把 Factory + Strategy + Observer 一起堆上；每加一个都要能指着一处真实坏味道说"它治的就是这个"。
