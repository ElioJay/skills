# 横切 / 特性追踪规则（trace-rules）

> 供 `code-read-deep-trace` 的阶段 1~6 使用。核心：分析对象是**一条贯穿系统的线索**（业务能力 / 关注点 / 数据项），**不是**某个容器（方法/文件/模块/项目）。
> 业内方法：feature/concern slicing、数据流与控制流追踪、software cartography（按线索测绘）。

---

## 一、追踪目标识别（阶段 1）
- 确认目标是**横切线索**：业务能力（下单、登录、退款）、关注点（认证、鉴权、缓存、事务、日志、限流、审计）、数据项（某字段 / 某 ID 从哪来、流到哪、被谁改）。
- 若用户给的是**单个容器**（`类名.方法名` / 单文件 / 单目录·包 / 整项目）→ 改道对应容器 skill（function / file / module / project），本 skill 不适用。
- 明确**追踪方向**：正向（源头/入口 → 下游/落点）、反向（现象/落点 → 上游/源头）、双向。

## 二、锚点定位（阶段 2）—— 找 seeds
- **关键词搜索**：按目标的领域词/类型名/注解/配置键全库 Grep（认证→`token`/`login`/`@PreAuthorize`；某字段→字段名/列名/DTO 名）。
- **入口锚点**：与目标相关的路由 / Controller / `main` / MQ 消费者 / 定时任务。
- **数据锚点**：目标数据的定义处（DTO / 实体 / 表 / 常量 / 配置）。
- 多语言/多框架：按生态找（注解、装饰器、中间件、配置、DI 绑定）。

## 三、跨文件跨模块追踪（阶段 3）
- 从 seeds 出发，沿**数据流**（赋值/传参/返回/持久化/序列化）与**控制流**（调用/分支/事件/中间件）逐跳追踪，**跨文件、跨模块**。
- **剪枝**：只跟与目标线索相关的边；无关分支不展开；trivial 跳过；第三方/标准库标叶子。
- **记录每一次"跳"**（跨文件/跨模块），标 `file:line`，这是 trace 区别于容器 skill 的核心产出。
- **动态/框架**：DI、反射、事件总线、中间件、路由处用 `reading-lenses.md` 的"运行期/框架"视角确认真实连接，边上标"（运行期绑定/框架约定）"。
- **深挖委派**：某一跳要读透 → 容器 skill（一个方法→`code-read-deep-function`、一个文件→`code-read-deep-file`、一个模块→`code-read-deep-module`、整项目→`code-read-deep-project`）。

## 四、涉及组件清单（阶段 4）→ ① 涉及组件图
- 汇总这条线索**流经的所有组件**（类/函数/文件/模块/外部系统），每个一句话"它在这条线索里干了什么"。

## 五、数据流与控制流（阶段 5）→ ② 端到端追踪流图
- 串出**端到端路径**：起点 → … → 终点；标数据形态变化与关键分支；标外部 IO（DB/HTTP/MQ/缓存/文件）。

## 六、断点与缺口（阶段 6）—— 本 skill 特有视角
- **断点**：线索到某点查不下去（动态分发未能定位实现、配置缺失、第三方黑盒、跨进程边界）→ 显式标"断点（原因）"，不假装贯通。
- **缺口 / 不一致**：同一关注点在某些路径有、某些路径没有（如鉴权漏了一条入口）；数据在某一跳被丢弃/被改写而无处理。
- 这些写入报告「断点与缺口」段；构成逻辑/流程硬伤的，另入「问题」段（见 `problem-checklist.md`）。

## 七、取舍原则
- **宁可标断点，不假装贯通**；任何未走通/未展开都显式声明。
- **主线优先**：分支多时沿最主要的那条线索深入，旁支浅尝即止并标注。
- **只读不改**：全程不编辑业务代码（符合家族定位与仓库规则）。
