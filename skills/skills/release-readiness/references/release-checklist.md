# 准出清单与判定口径

本文件给出逐项检查的判定口径：**什么算通过、什么算阻塞**。检查项按"缺少它会导致什么后果"排序，不是按文档顺序。

## 1. 范围与基线

| 检查项 | 通过 | 阻塞 |
|---|---|---|
| 发布范围 | 版本号、目标环境、纳入的需求与缺陷编号齐全，并能列出本次实际带上线的提交 | 范围说不清、或"还有几个改动没确认" |
| 代码基线 | 记录提交 SHA 或 tag，且构建与该基线对应 | 产物来自未记录的提交或本地未推送的改动 |
| 冻结后变更 | 清单为空；或有变更单、有理由、且已重跑受影响验证 | 冻结后仍有未评估的变更 |
| 版本一致性 | 版本号在代码、产物、文档三处一致 | 三处不一致或靠人工记住 |

## 2. 质量与产物

| 检查项 | 通过 | 阻塞 |
|---|---|---|
| 质量门 | 约定的测试与检查全绿，且能说明它跑的是哪个提交 | 无记录、或跑的是旧提交 |
| 已知失败 | 逐条列出并有处置结论（修、降级、接受并说明影响） | 有失败但没人判定影响 |
| 构建产物 | 制品清单齐全、有校验值、可复现或可追溯 | 产物来源不明、校验值缺失 |
| 配置差异 | 相对上个版本的配置增删改已列出；密钥只写来源不写值 | 存在"上线时再改"的配置 |

## 3. 数据与兼容

| 检查项 | 通过 | 阻塞 |
|---|---|---|
| 库表变更 | 脚本与执行顺序明确，且有 `database-migration` 的迁移与恢复口径 | 变更未评审或顺序靠记忆 |
| 新旧并行 | 新旧版本同时运行期间，读写两侧都成立 | 只验证了新版本 |
| 回填 | 耗时估算、分批或失败续跑方式、前后校验方式明确 | 一次性全量回填且无失败处理 |
| 不可逆操作 | 单独列出并给出前向修复路径 | 把删字段/删表/数据清洗混进"回滚即可" |

## 4. 观测与放量

| 检查项 | 通过 | 阻塞 |
|---|---|---|
| 关键指标 | 明确这次发布要盯哪些指标与日志，以及它们的正常范围 | 没有观测手段 |
| 观测窗口 | 给出时长与值守人；窗口时长与流量周期匹配 | 发完就没人看 |
| 放量判据 | 每批的进入条件与停止条件可判断 | "看着没问题就继续" |
| 异常处置 | 谁有权决定停止放量或回滚，联系方式明确 | 无人可决策 |

## 5. 回滚

| 检查项 | 通过 | 阻塞 |
|---|---|---|
| 触发条件 | 可观测、可判断，含阈值与持续时间 | "感觉不对就回滚" |
| 步骤 | 每步有操作入口、执行角色、预计耗时、验证方式 | 只有"回滚到上一版本"一句话 |
| 数据影响 | 说明回滚后数据是否一致、是否需要补偿 | 未评估数据影响 |
| 验证状态 | 已演练，或明确标注"未验证"并说明风险 | 声称可用但无任何证据 |
| 耗时 | 给出实际耗时估算与依据 | 耗时未知且影响决策 |

## 判定口径

- **可以发**：以上各项均通过，或未通过项已逐条给出被接受的处置结论及其影响说明。
- **不能发**：存在任何一项阻塞项，且该项缺少处置结论。**报出"不能发"是本 skill 正常工作，不是失败。**
- 介于两者之间时，写清"可以发的前提是 X 在 Y 之前完成"，不要用"风险可控"含混过关。

## 常见反模式

- 把"测试都过了"当作全部证据，忽略配置差异与观测准备。
- 回滚预案只在文档里存在，从未在预发执行过。
- 灰度批次没有停止条件，等价于全量发布。
- 冻结后继续合并代码，却不重跑验证。
- 发布说明只写"优化若干问题"，无法追溯到底改了什么。
