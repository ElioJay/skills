# 指标与日志

从关键路径推导监控点，再把监控点落成指标、日志与追踪三类数据。**顺序不能反**：先有故障模式，再有监控点，最后才有具体指标名与字段名。

## 1. 从关键路径推导监控点

对每条关键路径走一遍这四个问题，答案就是监控点清单：

| 问题 | 推导出的监控点 |
|---|---|
| 这条路径上，用户在哪里会感知到"慢"？ | 延迟类：端到端耗时、各段依赖耗时、排队等待时间 |
| 单位时间内有多少这样的请求？ | 流量类：QPS、消息速率、并发数 |
| 什么情况算"这次请求失败了"？ | 错误类：错误率、超时数、重试数、部分成功数 |
| 用什么资源来承接这些请求，余量还剩多少？ | 饱和度类：线程池/连接池、队列深度、CPU/内存/磁盘/配额 |

再对每条故障模式补一个**能区分"是这条路径坏了"与"整个系统都慢了"**的维度：接口模板、依赖名、错误类别。没有这个维度，告警响了也定位不到路径。

失败路径同样要观测：**部分成功**（扣款成功但发货失败）、**静默失败**（任务没跑但没人报错）、**降级生效**（熔断/兜底返回被当成成功统计）。这三类最容易在只看错误率时被漏掉。

## 2. 四类信号与指标类型对照

| 信号 | 指标类型 | 例子 | 查询口径 |
|---|---|---|---|
| 延迟 | histogram / summary | 请求耗时、依赖调用耗时 | P50 / P95 / P99，按接口模板分组 |
| 流量 | counter | 请求总数、处理消息数 | `rate(x[5m])` |
| 错误 | counter | 错误总数、超时总数 | 错误数 / 总请求数，注意分母口径 |
| 饱和度 | gauge | 队列深度、连接池占用、使用率 | 当前值 + 相对容量上限的比例 |

类型选择的常见错误：

- 用 counter 直接看瞬时值：counter 只增，重启还会归零，单看数值毫无意义。
- 用 gauge 算速率：gauge 会上下跳，差值不等于流量。
- 用"平均耗时"当延迟指标：见下一节。
- 用 counter 统计"当前进行中的请求数"：这本质是 gauge，用 counter 需要自己配 `inc`/`dec` 且容易算错。

## 3. 分位与采样

**禁止用平均值掩盖尾延迟。** 平均值把慢请求稀释掉，而用户体验由尾部决定。设计时明确写出：

- 用哪个分位：对外接口一般看 P95 与 P99；内部批处理与定时任务看 P99 与最大值；不要只报 P50。
- 时间窗多长：短窗（1~5 分钟）用于告警，长窗（1 天~30 天）用于趋势与 SLO。
- 样本量够不够：低流量接口的 P99 可能只是几个样本，不要据此设敏感告警。低流量接口改用"长窗口下的错误计数 + 绝对阈值"更稳。
- 直方图桶（bucket）要按该路径的实际耗时分布设置，桶全挤在一个区间时分位数是假的。

**采样**：

- 追踪采样：高峰期可降采样，但**错误与慢请求必须保留**（尾采样或按结果采样），否则最该看的样本会被采掉。
- 日志采样：对高频重复日志可按比例采样，但**错误、异常与关键业务事件不采样**。
- 指标一般不做采样，靠聚合与维度基数控制成本。

## 4. 标签基数控制

**高基数维度不得作为指标标签**：`user_id`、订单号、交易号、完整 URL（含路径参数与查询串）、traceId / spanId、session id、时间戳、原始错误消息、任意自由文本。

原因只有两条，但都致命：

1. **成本**：时间序列数 = 各标签取值的笛卡尔积。加上 `user_id` 后，序列数量随活跃用户数增长，存储、写入与查询成本跟着业务量线性上涨。
2. **查询退化**：聚合、面板刷新与告警计算都变慢，最后慢到没人打开看板，观测手段自然失效。

控制办法：

- **归一化维度**：路径参数替换成模板（`/orders/{id}`）；错误消息归类到有限枚举（`timeout` / `refused` / `validation`）。
- **高基数标识下沉**：需要按人、按单、按请求号排查时，去**日志与追踪**里查那一次请求，不要做成指标维度。
- **按需聚合**：确实要按客户看，先用有限的分层（大客户 / 中小客户）或按需聚合的离线口径，而不是给每个客户一条序列。
- **给每个维度写基数上限**：设计时估算取值上限，超预算的维度换掉或下沉。

## 5. 日志字段规范与脱敏

### 字段规范

| 字段 | 必填 | 说明 |
|---|---|---|
| 时间戳 | 是 | ISO 8601 或带时区的本地时间，精度到毫秒 |
| 级别 | 是 | ERROR / WARN / INFO / DEBUG，语义一致，别把正常分支记成 ERROR |
| 消息 | 是 | 自包含、可检索；不要只写 `failed` |
| traceId / requestId | 是 | 与追踪系统同源，用于串起一次请求 |
| 服务名与实例 | 是 | 多实例部署时必须能区分是哪个实例 |
| 关键业务标识 | 按路径 | 订单号、任务 ID、租户、操作类型等，用于按业务定位 |
| 耗时 | 建议 | 跨服务调用与慢操作记录耗时，便于与指标对照 |
| 异常堆栈 | 异常时必填 | 类型 + 消息 + 堆栈，不要只记消息 |
| 上下游标识 | 建议 | 上游请求 ID、下游响应码，便于划清责任边界 |

结构化输出（JSON 或等价键值）优先；关键信息用独立字段承载，不要拼进一句话。

### 脱敏

**不得记录密钥、令牌、口令与个人敏感信息。** 具体禁止落盘的包括：密码与口令、`Authorization` 头与各类 token、Cookie 与 session、密钥与证书内容、身份证号、银行卡号与支付凭证、手机号、邮箱、详细地址、健康与生物特征信息。

做法：

- 需要定位时记录**脱敏形态**：尾号、哈希、掩码（如 `138****0000`）、或只记录"是否存在"这一布尔事实。
- 在采集或序列化层做统一脱敏，而不是靠每个调用点自觉；在方案里写明脱敏发生在哪一层。
- 排查用的原始报文如需留存，放入受控的临时通道并写明保留期限，不要进常规日志。

### 关联性

**日志无关联 ID 是头号反模式**：没有 traceId/requestId 的日志在分布式系统里几乎无法用于定位，只能靠时间戳猜。字段规范里 traceId 是必填项，不是可选项。

## 6. trace 上下文透传点清单

逐项检查，缺失的就是断链点：

1. **线程池与任务队列**：提交任务时把上下文（traceId、MDC、请求头）随任务一起带过去，或在池内做装饰包装。直接用池执行、上下文只在原线程里有效，就会断。
2. **异步任务与回调**：`then` 链、事件回调、定时回调里可能已经切了线程；进入回调前重新绑定上下文。
3. **响应式与协程调度**：线程切换点（调度器）需要显式携带上下文，否则中途丢失。
4. **MQ 生产与消费**：生产端把 traceId 写入消息头/属性，消费端从消息里读出并绑定；不要以为消息天然带着追踪上下文。
5. **跨服务调用**：出站 HTTP/RPC 注入透传头，入站侧读取并延续；头名与格式要跨团队约定一致。
6. **服务网格 / 网关 / 反向代理**：确认这些中间层不会剥掉透传头。
7. **定时任务与批处理**：没有上游请求，需要自己生成新的 traceId，并把业务标识（批次 ID、任务 ID）写进日志与 span 属性。
8. **跨语言与跨团队边界**：双方使用不同的追踪实现时，约定最小公共头（traceId + 采样标志）。
9. **线程本地上下文的清理**：用完要清，否则线程复用时会串上下文，日志里出现别人的 traceId。
10. **降级 / 兜底路径**：走熔断或兜底逻辑时同样要记 trace，否则"看不到"的路径恰恰是最需要看的。

## 7. 常见反模式

- **只测 CPU**：把资源指标当成全部观测手段。CPU 正常而用户大量失败是完全可能的（依赖挂了、逻辑错了、额度用完）。四类信号必须齐。
- **只告警不行动**：告警没有对应的处置步骤，值班只能围观。见 `alerting-and-runbook.md`。
- **日志无关联 ID**：没有 traceId/requestId，跨服务定位只能靠猜。
- **只看平均值**：用平均耗时掩盖尾延迟，改完"平均变好了"而用户依然慢。
- **把每个异常都记成 ERROR 并告警**：噪音淹没真问题。
- **指标维度塞业务标识**：基数爆炸，成本上升、查询变慢。
- **只看成功率不看部分成功**：扣款成功发货失败在成功率上可能毫无波动。
- **看板堆满面板没有结论**：每个面板都应回答一个具体问题，否则删掉。
