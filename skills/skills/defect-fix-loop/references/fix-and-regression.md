# 从复现到修复与回归

这一段是缺陷修复的执行细节：怎么把复现变成失败测试、最小改动的边界在哪、回归范围怎么推导、验证证据给到什么程度算够。

## 1. 从复现到失败测试

**先有失败测试（或等价的最小复现证据），再改代码。** 顺序反了，就失去了判断"改对了没有"的基准。

### 做法

1. **把复现步骤翻译成测试**：给定同样的前置数据与操作序列，断言**期望行为**（不是断言当前行为）。断言必须能区分"修好了"与"没修"。
2. **确认它在修复前失败**：跑一次，把失败输出留下来。失败必须是**因为缺陷本身**，而不是因为测试写错、环境没配好或数据没构造对——注意区分"我的测试红了"和"缺陷红了"。
3. **失败要红得准确**：断言失败的信息应能指出差异在哪里。只写 `assertTrue(result)` 这种测试，修复前后都可能通过，毫无价值。
4. **尽量贴近缺陷层级**：能单元测试就单元测试（跑得快、定位准）；缺陷只在集成环境下出现（依赖、并发、消息）就写集成或组件测试。
5. **最小复现证据的等价形态**：确实无法自动化时，留下可重复执行的东西——一条能复现的 SQL、一段脚本、一份固定的请求报文、一套手动操作步骤 + 期望/实际对照。并在记录里写明**为什么不能自动化**（环境依赖、人工审核环节、外部系统不可 mock 等）。

### 常见错误

- 先改代码再补测试：测试会被"当前行为"污染，变成给错误行为背书。
- 断言写得过松：修复没做对也能通过。
- 测试依赖执行顺序或共享数据：第二次跑就假绿。
- 把不稳定（flaky）测试当基准：先确认它是稳定失败，再开始修；偶发失败要写明概率与触发条件。

## 2. 最小改动的边界

### 可以改（允许的改动）

- 与缺陷直接相关的**判断条件、边界值、空值分支、类型转换、状态流转**。
- 直接导致问题的那一处**调用参数或返回处理**。
- 为修复所必需的**针对该缺陷的测试**与测试数据构造。
- 缺陷根因所在的那一处**配置项取值**（不改结构）。

### 不可顺带改（需要先确认）

- **重构**：提取方法、改类结构、改命名、拆文件、调整分层。
- **格式化与风格统一**：整文件重排、调整缩进与换行、批量补注释。
- **依赖升级**：库版本、框架版本、构建工具版本。
- **无关清理**：删死代码、改日志级别、调无关配置。
- **接口与公共方法签名变更**：会影响调用方，属于范围扩大。
- **测试体系改造**：换测试框架、改断言库、重排测试目录。
- **为了让测试通过而放宽或跳过测试**（明确禁止，见下）。

### 为什么这条边界很重要

修复的价值在于**可验证的因果关系**：改了 A，缺陷消失。夹带无关改动后：

- 评审无法判断到底是哪一处消除了缺陷；
- 回归范围被迫扩大（因为改动面变大了），验证成本上升；
- 出了问题无法快速回退到"只有修复"的状态。

### 明确禁止

- **禁止为了让测试通过而删、跳过、禁用或弱化测试**：不改 `skip` / `ignore` / `xfail`，不注释掉用例，不删断言。
- **禁止把断言改宽以掩盖缺陷**：把精确比对改成"非空"、把容差调大、把超时阈值放宽、把期望值改成实际值——这些都是把缺陷藏进测试里。
- 如果测试确实写错了（期望本身违反已确认的需求），那是**改测试的正确理由**，但必须写明依据（需求文档、接口契约、用户确认），并说明为什么这不是在为通过而放宽。**分不清是"测试错"还是"实现错"时，先问，不要改。**

## 3. 回归范围推导

**"跑一遍全量测试就行"不是回归推导。** 全量测试覆盖率有限，且跑不出与本次改动相关的时序、权限、数据行为。回归范围要按影响面推：

### 推导清单

1. **直接调用方**：谁调用了被改的方法 / 接口 / 服务？逐个列出，判断每个调用方的输入范围是否覆盖改动后的新行为（尤其原调用方依赖的旧行为被改变了的情况）。
2. **间接调用方与公开契约**：被改的东西是否对外暴露（HTTP 接口、消息格式、SDK、CLI 输出）？对外行为的改变要考虑兼容性。
3. **共享工具与公共方法**：改的是不是被多个模块共用的工具、基类、拦截器、序列化器、异常处理器？这类改动的爆炸半径远大于看起来的样子。
4. **边界条件与空值**：空、null、零、负数、极大值、超长字符串、Unicode、空集合、单元素集合、时间边界（跨天、跨月、时区、夏令时）。
5. **并发与时序**：多线程 / 多实例同时操作、幂等性与重复提交、加锁范围、缓存与数据库的一致性窗口、消息乱序与重复投递、事务边界。
6. **权限与多租户**：不同角色、不同租户之间的数据隔离；改动是否可能让越权访问成立或失效。
7. **数据迁移与兼容**：改动是否涉及字段语义、枚举取值、存量数据格式；旧数据读到新代码、新数据被旧代码读到会怎样。
8. **相关既有用例**：仓库里已经存在的、覆盖同一模块或同一路径的测试——按模块名、包名、接口名检索出来，列入回归清单。
9. **反向路径**：失败路径、超时与重试路径、降级与兜底路径，这些往往没有测试覆盖，却是缺陷最爱藏的地方。

### 结果怎么写

逐项写出：**范围项 → 要跑什么 / 要验什么 → 结果**。没跑的项要写清为什么没跑（环境不可用、场景不可构造），并归入"未验证项"。**不把这些算作已回归。**

## 4. 验证证据的层次

按缺陷影响面选层次，不必一律跑全量：

| 层次 | 适用 | 证据形态 |
|---|---|---|
| **单元** | 缺陷局限在单个函数 / 类 / 纯逻辑 | 失败测试由红变绿的输出 |
| **组件 / 集成** | 缺陷跨越两个组件、涉及数据库、消息、外部依赖 | 集成测试输出；修复前后的请求/响应或数据快照 |
| **端到端** | 缺陷在主流程上、用户可感知、跨多个服务 | 端到端用例输出或手动走查记录（步骤 + 期望 + 实际） |

选择原则：**证据的层次要能覆盖缺陷发生的层次**。缺陷在端到端才出现，单元测试全绿不能证明修好了；缺陷只在某个分支上，跑通主流程也不能证明修好了。

### 必须有的东西

- **前后对照**：修复前的失败输出与修复后的通过输出（同一命令、同一环境）。
- **复现步骤对照**：修复前能复现、修复后不能复现。
- **真实输出**：贴命令与真实结果，不写"应该可以通过"。**不得声称未运行的测试已通过。**

## 5. 无法验证时怎么写

拿不到环境、构造不出数据、依赖第三方或人工环节时，如实报告，不要含糊：

- **明确状态**：写"未验证"，不写"应该没问题""理论上已修复"。
- **说明原因**：为什么验证不了（缺少环境 / 数据不可构造 / 依赖外部系统 / 需要人工审批）。
- **给出替代证据**：代码走查结论、单元层验证结果、相同逻辑在别处的既有测试结果——并明确标注这些是**间接证据**。
- **给出验证计划**：需要谁、在什么环境、按什么步骤验证；以及验证通过前这项修复的状态是"待验证"。
- **给出观察期建议**（适用于只能上线后观察的缺陷）：观察什么指标/日志、观察多久、出现什么现象算没修好。
- **说清风险**：在验证之前，这个缺陷是否应该被当作已修复对待（默认不应该）。
