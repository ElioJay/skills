# 图谱清单（51 张）· 判据 · 粒度矩阵

阶段 4「定图谱」时读这份文件。**它的用法不是照单全画，而是照单排除。**

---

## 一、挑图算法

```
输入：阶段 3 的事实档案（含项目类型标记）+ 粒度
输出：图单 + 不画清单（每条带原因）

1. 按粒度取候选集（见第二节矩阵），不在候选集里的直接排除
2. 候选集里的 ⭐ 全部入选，除非事实档案明确证否
3. 候选集里的 ○ 逐条对「触发判据」，命中才入选
4. 候选集里的 ⚠ 默认排除，事实档案有硬证据才入选
5. 入选后做一次「删除测试」：这张图去掉之后，读者的理解有损失吗？没有 → 删掉
6. 项目级超过 30 张 → 按「主要读者」合并同类项；模块级超过 15 张、入口级超过 8 张 → 同理
7. 排除的每一条都要写进索引，格式：「XX 图 —— 未画，原因：YY」
```

**「明确证否」的例子**：⭐ 的 #16 状态机图在候选集里，但事实档案的项目类型标记写着「未发现有状态实体」，就排除，并在索引写「状态机图 —— 未画，原因：未发现带状态迁移的实体（无 status/state 字段的多态迁移）」。

## 二、粒度 × 图种矩阵

| 粒度 | 候选集 | 典型入选张数 |
|---|---|---|
| **项目级** | 全部 51 张 | **25~30** |
| **模块级** | 3,4,5,10,11,13,14,15,16,18,20,21,25,26,27,28,29,33,42,44,51 | **10~15** |
| **方法入口级** | 5,13,14,15,18,20,21,25,27,29 | **6~8** |

粒度会改变同一编号图的形态：

| # | 项目级形态 | 模块级形态 | 入口级形态 |
|---|---|---|---|
| 5 依赖图 | 模块间依赖 + 环检测 | 模块内文件/子包依赖 + 环检测 | **上下游关系图**：上游调用方 → 本方法 → 下游被调用 |
| 4 分层 | 全系统分层 | 模块内分层（web→service→dao） | 不适用 |
| 13 流程 | 端到端业务流程 | 模块内主流程 | **本方法的分支逻辑图** |
| 25 数据流 | 端到端 DFD | 模块进出的数据流 | 入参 → 中间形态 → 返回值 / 落库 |
| 26 ER | 全库表关系 | 本模块拥有的表 | 不适用 |

## 三、类别一：架构与结构（#1~#12）—— 系统长什么样

| # | 图 | 回答什么问题 | Mermaid | 触发判据 |
|---|---|---|---|---|
| **1** ⭐ | **系统上下文图** | 谁在用这个系统、它依赖哪些外部系统 | `flowchart TB` + subgraph | 恒画。用户说「架构图」时通常指的就是这张 |
| **2** ⭐ | **容器/部署单元图** | 由哪些可独立部署的东西组成、之间怎么通信 | `flowchart TB` | 恒画。单体项目也画（只有一个容器也要说清它连了什么） |
| 3 ○ | 组件图 | 单个容器内部怎么划分组件 | `flowchart TB` | 单个容器内组件 ≥ 6 个，或容器图里某个盒子明显是黑箱 |
| **4** ⭐ | **分层架构图** | 有几层、依赖方向、有没有跨层调用 | `flowchart TB` + subgraph | 恒画。**跨层调用要用虚线特殊标出**，这是这张图的主要价值 |
| **5** ⭐ | **依赖图（含环检测）** | 谁依赖谁、有没有循环依赖 | `flowchart LR` | 恒画。**必须下环检测结论**（有环列出 / 无环写明），只画图不下结论等于没画 |
| 6 ○ | 部署拓扑图 | 跑在哪些机器 / 容器 / 可用区上 | `flowchart TB` + subgraph | 有 Dockerfile / k8s manifest / docker-compose / 部署脚本 / IaC |
| 7 ○ | 网络与信任边界图 | 流量从哪进、在哪跨信任边界 | `flowchart LR` + subgraph | 有网关 / 反向代理 / VPC 配置 / 多套鉴权域 / 内外网分区 |
| 8 ○ | 技术栈全景图 | 各模块用什么语言、框架、中间件 | `mindmap` 或 `flowchart LR` | **polyglot 项目必画**；单语言但框架 ≥ 4 个也画 |
| 9 ○ | 目录结构职责图 | 每个顶层目录是干嘛的 | `mindmap` | 目录命名不自解释（`core/` `common/` `util/` 这类），或顶层目录 ≥ 8 个 |
| 10 ○ | 核心域类图 | 核心对象的字段、继承、组合关系 | `classDiagram` | 有明确的领域模型（实体 / 值对象 / 聚合根）；纯 CRUD 项目不画，交给 #26 ER 图 |
| 11 ○ | API 全景图 | 对外一共有哪些入口 | `flowchart LR` + 表 | 对外端点 ≥ 8 个。**图给分组，表给完整清单**——别想在图里塞下所有端点 |
| 12 ⚠ | 扩展点/插件图 | SPI、Hook、策略注册在哪、怎么被发现 | `flowchart TB` | 有 SPI / `ServiceLoader` / 插件目录 / 策略注册表 / 事件钩子机制 |

## 四、类别二：行为与流程（#13~#24）—— 系统怎么跑

| # | 图 | 回答什么问题 | Mermaid | 触发判据 |
|---|---|---|---|---|
| **13** ⭐ | **核心业务流程图（含分支）** | 主链路怎么走、判定点在哪、每个分支通向哪 | `flowchart TD` | 恒画。**只有主干没有分支的流程图是半成品** |
| **14** ⭐ | **主链路时序图** | 参与者之间的调用顺序与时机 | `sequenceDiagram` | 参与者 ≥ 3 个就画。参与者只有 2 个时并入 #13 |
| **15** ⭐ | **异常/超时/降级路径图** | 失败怎么走、超时怎么走、熔断重试兜底在哪 | `sequenceDiagram` + `alt`/`opt` | 恒画。**这是排障时唯一真会被打开的行为图**，也是最容易被漏掉的一张 |
| 16 ○ | 状态机图 | 有状态对象的合法迁移与非法迁移 | `stateDiagram-v2` | 事实档案里有**带状态迁移的实体**（`status` / `state` 字段被多处改写，或有显式状态枚举）。无状态项目**绝不硬画** |
| 17 ○ | 泳道图 | 跨角色 / 跨团队 / 跨系统的职责边界在哪 | `flowchart LR` + subgraph | 流程跨 ≥ 3 个角色或 ≥ 2 个系统，且职责边界是这个流程的关键难点 |
| 18 ○ | 调用链图 | 一个入口往下调到哪、调用树多深 | `flowchart TD` | **入口级恒画**；项目/模块级只对最核心的 1~2 条链路画 |
| 19 ○ | 事件/消息拓扑图 | 谁发谁收、重试队列与死信怎么走 | `flowchart LR` | 有 MQ / 事件总线 / 消息中间件依赖（Kafka / RabbitMQ / RocketMQ / Redis Stream / 领域事件） |
| 20 ○ | 并发与锁图 | 临界区在哪、锁粒度多大、竞态长什么样 | `sequenceDiagram` 或 `flowchart TD` | 有显式锁 / 信号量 / 乐观锁版本号 / 分布式锁 / 线程池 / 协程池 |
| 21 ○ | 决策树/规则图 | 复杂判定怎么走 | `flowchart TD` | 单个方法或规则集的判定分支 ≥ 5 个（风控、路由、定价、权限判定这类） |
| 22 ○ | 定时任务调度图 | 有哪些 job、几点跑、互相依赖吗 | `gantt` 或 `flowchart LR` | 有 cron / `@Scheduled` / Celery beat / k8s CronJob / 调度平台配置 |
| 23 ○ | 启动/初始化时序图 | 进程起来时按什么顺序装配 | `sequenceDiagram` | 启动顺序有隐含依赖（DI 装配顺序、预热、迁移脚本、健康检查门槛）且踩过坑 |
| 24 ⚠ | 用例图 | 角色 × 能力的对应关系 | `flowchart LR` | 角色 ≥ 4 个且权限差异大。多数代码库用 #1 上下文图 + #11 API 全景就够了 |

## 九、不画的图怎么写进索引

排除的每一张都要在 `README.md` 里留一行，**写原因而不是只写"未画"**：

```markdown
## 未画的图

| 图 | 原因 |
|---|---|
| 状态机图（#16） | 未发现带状态迁移的实体：全库无 status/state 字段的多态迁移 |
| 事件/消息拓扑图（#19） | 无 MQ 依赖：构建文件里没有任何消息中间件客户端 |
| 分库分表图（#32） | 单库单表，无分片中间件 |
| 团队所有权图（#50） | 无 CODEOWNERS 文件，代码里读不出归属，不猜 |
```

这一段的价值：**读者知道「没画」是判断过的结果，而不是漏了**。评审时这一段比多画五张凑数图更能说明你读懂了这个系统。

## 十、常见挑图错误

| 错误 | 后果 | 怎么改 |
|---|---|---|
| 六大类平均用力，每类都画几张 | 无 MQ 项目里出现消息拓扑图，无状态项目里出现状态机图 | 挑图看事实档案的项目类型标记，不看类别平衡 |
| ⭐ 无脑全画 | 纯库项目画出了排障决策树 | ⭐ 也要过「明确证否」这一关 |
| 只画 happy path 类的图，跳过 #15 #40 | 排障时最需要图，却恰好没有 | #15 异常路径 与 #40 排障决策树 是骨架的一部分 |
| 入口级粒度画架构图 | 一个方法哪来的架构？画出三个方框的废图 | 严格按第二节矩阵取候选集 |
| 项目级画到 40 张 | 读者放弃 | 超过 30 张就按「主要读者」合并同类项 |
| 排除的图不写原因 | 读者以为漏了，或以为系统里没有这东西 | 第九节的格式，逐条写原因 |
