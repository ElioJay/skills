# 高频工程 / 架构模式

> 这些不是 GoF 经典，但后端日常最常纠结。每个模式同样先过 **YAGNI 闸门**：没有第二个使用点，先别造。

---

## 依赖注入（DI）

**意图**：把依赖的创建权交给外部（容器 / 调用方），对象只声明"我需要什么"。

**何时用**
- 需要可测试性（替换真实依赖为 mock）
- 多处复用同一实现，或运行时可切换

**何时别用**
- 工具函数 / 纯计算逻辑，无外部依赖
- 简单脚本，上下文里传参即可

**代价**：引入框架（Spring / Wire 等）增加启动复杂度；过度 DI 导致依赖图难以追踪。

**最简替代**：构造函数直接传参，或模块级单例变量——在没有测试需求或只有一个实现时完全够用。

---

## Repository

**意图**：把数据访问逻辑封装在一个"集合状"对象后面，业务代码不直接碰 SQL / ORM。

**何时用**
- 同一聚合有多种存储后端（DB + 缓存 + 远程 API）
- 数据访问逻辑复杂、多处复用
- 需要在测试中 mock 存储层

**何时别用**
- 只有一个存储后端（MySQL），且查询逻辑简单、只是 CRUD
- ORM（MyBatis / JPA / GORM）已经提供了足够的抽象

**代价**：多一层 indirection，方法爆炸（`findByXxx` 越写越多），维护成本上升。

**最简替代**：直接用 ORM / DAO，不套 Repository。薄 CRUD 套 Repository 只是转调一层，没有任何收益。

---

## DTO / VO

**意图**：在层间或系统间传递数据，与领域模型解耦，避免暴露内部结构。

**何时用**
- 对外 API 响应需要裁剪字段、脱敏、格式转换
- 跨服务 RPC，需要稳定的序列化契约
- 领域对象含懒加载 / 循环引用，直接序列化会爆

**何时别用**
- 小项目 / 内部接口，实体字段就是想要的响应字段
- CRUD 项目里"为了分层而分层"造 DO / BO / DTO / VO 四套对象——能用一个实体就别造四层

**代价**：大量 boilerplate 转换代码；字段改动要同步多处；BeanUtils.copy 的"哑转换"极易漏字段。

**最简替代**：直接返回实体（或 Map），加 `@JsonIgnore` 排除不要暴露的字段。规模达到需要独立版本的 API 契约时再引入 DTO。

---

## Specification（规格）

**意图**：把业务规则封装为可组合的判断对象（`and` / `or` / `not`），解耦查询条件构建与执行。

**何时用**
- 筛选条件组合爆炸，动态拼接逻辑极其复杂
- 规则本身需要复用或单独测试

**何时别用**
- 查询条件固定或只有寥寥几种组合
- ORM 的动态查询 API（QueryWrapper / Criteria / Predicate）已够用

**代价**：额外抽象层，初学者难理解；对简单查询是大炮打蚊子。

**最简替代**：在 DAO / Repository 方法里直接用 ORM 的条件构建 API，或写静态查询方法。

---

## Unit of Work

**意图**：追踪一个业务操作内所有变更，在最后统一提交，保证原子性。

**何时用**
- 框架不带事务管理，需要手动批量提交
- 多个聚合根变更要放在同一事务

**何时别用**
- 已有 Spring `@Transactional` / Django ORM transaction / GORM Begin-Commit 管理事务
- 框架已隐式实现 UoW（绝大多数 ORM 都有 Session / EntityManager）

**代价**：手动实现复杂，易出 dirty-read / 忘记 flush 等问题。

**最简替代**：用框架提供的事务注解（方法级）。不要在已有 ORM 的情况下自己再造一层 UoW。

---

## Service Layer（服务层）

**意图**：封装应用逻辑，协调领域对象、基础设施（DB / MQ / 外部 API）完成用例。

**何时用**
- 用例逻辑跨多个实体 / 外部调用，放在 Controller 里太臃肿
- 逻辑需要被多个入口（HTTP / 消息队列 / 定时任务）复用

**何时别用**
- 简单 CRUD，Service 只是透传 DAO——此时 Service 是无意义中间层

**代价**：贫血模型陷阱：所有业务逻辑流入 Service，领域对象退化成纯数据袋，Service 膨胀成巨类（Big Service）。

**最简替代**：简单接口直接在 Controller 里调 DAO / ORM，等逻辑变复杂再抽 Service。一个 Service 方法不超过一屏时警惕是否过度拆分。

> **特别注意**：为单一实现造 `XxxService` 接口 + `XxxServiceImpl` 是常见过度设计。没有第二个实现、没有 mock 需求时，直接写 `XxxService` 具体类即可。

---

## Value Object（值对象）

**意图**：用不可变对象表达无身份标识的概念（Money、Email、Address、DateRange）。

**何时用**
- 多个属性在概念上是一个整体，且只通过值判断相等
- 该概念在多处出现，携带自己的验证规则

**何时别用**
- 概念简单、只在一处使用，直接用基本类型更清晰
- 语言 / 框架的 ORM 映射对 Value Object 支持不好（嵌入表还是 JSON 列成本高）

**代价**：不可变性在某些语言实现繁琐；ORM 持久化需要额外配置。

**最简替代**：用带基本类型字段的 POJO / dataclass，加静态工厂方法做校验。等该类型在三处以上被复用再提升为 VO。

---

## Null Object

**意图**：用一个"什么都不做"的对象替代 null，消除调用方的 null 检查。

**何时用**
- 大量防御性 `if (x != null)` 散落各处，逻辑相同
- 某个依赖有"可选"语义，缺失时走 no-op 行为

**何时别用**
- null 需要被区分对待（"找不到" vs "未设置" 语义不同）
- 只有一两处 null 检查，用 Optional / Elvis 运算符更简单

**代价**：引入额外类，调试时难以发现"为什么什么都没发生"——隐藏了本该显式处理的缺失情况。

**最简替代**：`Optional<T>` / Kotlin nullable / 三元 null 检查。规则：三处以上相同 no-op 逻辑才值得引入 Null Object。

---

## 轻量 CQRS

**意图**：读模型（Query）与写模型（Command）分离，各自优化——写走领域模型保证一致性，读走扁平化视图/缓存保证性能。

**何时用**
- 读写模型差异显著（读需要聚合多表、写只改一个聚合根）
- 读侧压力远大于写侧，需要独立扩展

**何时别用**
- 简单 CRUD——读写模型几乎相同，CQRS 只加复杂度
- 团队规模小、系统初期——等读写模型真正分化、读侧压力真出现再引入；提前上是过度设计
- **绝对不要**把轻量 CQRS 当"新鲜感"理由用在标准管理后台 / 单体小项目

**代价**：两套模型需同步演化；引入事件溯源后复杂度指数上升；调试难度大。

**最简替代**：Service 方法区分 `queryXxx` / `saveXxx`，返回不同 DTO——这已经是"逻辑 CQRS"，完全够用。等读写有明确的独立部署需求再走物理分离。

## 过度设计速查

| 反模式 | 信号 | 替代方案 |
|--------|------|----------|
| 全套 DO/BO/DTO/VO 四层 | 转换代码 > 业务代码 | 按需引入，CRUD 用一个实体 |
| 简单 CRUD 上 CQRS/事件溯源 | 读写模型几乎相同 | 先用普通 Service + DTO |
| ORM 上套薄 Repository | Repository 只是 `return dao.findXxx(...)` | 直接用 ORM/DAO |
| 单实现 ServiceImpl + 接口 | 没有第二个实现，没有 mock 需求 | 直接写具体类 |
| 每个字段都是 Value Object | VO 比业务代码还多 | 先用基本类型，复用 3 次再抽 |
| 提前引入 Specification | 查询条件固定，只有 2-3 种 | ORM 动态条件 API |

> **闸门规则**：引入任何模式前先问——"如果不用它，最简单的写法是什么？那个写法到底有什么不够？"能清楚回答才上，答不出就别上。
