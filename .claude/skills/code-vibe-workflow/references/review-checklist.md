# Code Review 维度清单

本文件是 code-vibe-workflow 第 5 阶段（Code Review）的配套清单。

---

## 总体打分模板

每次 Review 后输出如下表格 + Top 3 必修问题：

```
| 维度       | 分数(1-5) | 关键问题 |
|------------|-----------|----------|
| 正确性     |           |          |
| 可读性     |           |          |
| 性能       |           |          |
| 安全       |           |          |
| 异常处理   |           |          |
| 测试覆盖   |           |          |
| 风格一致性 |           |          |

Top 3 必须修复：
1. ...
2. ...
3. ...
```

**评分基准**：
- 5 = 无可挑剔，可合并
- 4 = 小瑕疵，建议改但不阻塞
- 3 = 中等问题，应修复
- 2 = 明显缺陷，必须修
- 1 = 严重缺陷，阻塞合并

---

## 维度 1：正确性

- [ ] 是否实现了 Plan 中列出的**所有**需求点？
- [ ] 边界场景是否覆盖：null、空集合、0、负数、超大值、并发？
- [ ] 是否处理了用户提的所有疑问（来自第 1 阶段）？
- [ ] 输入校验是否完整？（必填、格式、范围）
- [ ] 返回值是否符合接口契约（字段名、类型、空值约定）？
- [ ] 是否存在"看起来对但实际跑不通"的代码？（命名冲突、未引入的包、笔误）

---

## 维度 2：可读性

- [ ] 命名是否自解释？避免 `temp`、`data`、`obj` 等无信息变量名
- [ ] 函数是否过长？单函数 > 50 行就该考虑拆分
- [ ] 嵌套层级是否 > 3 层？考虑提前 return 或抽函数
- [ ] 注释是否到位？（写 WHY 不写 WHAT；CLAUDE.md 要求加注释）
- [ ] 是否有"魔法数字" / "魔法字符串"？应抽常量
- [ ] 复杂逻辑是否有一句话注释解释意图？

---

## 维度 3：性能

- [ ] **N+1 查询**：循环内是否在调数据库/远程接口？
- [ ] **全量加载**：是否把整个大表读进内存？应分页/流式
- [ ] **死循环 / 无界递归**：终止条件是否清晰？
- [ ] **大对象**：是否把 MB 级数据放在内存里反复 copy？
- [ ] **缓存**：高频读 + 低频写的场景是否考虑了缓存？
- [ ] **同步阻塞**：耗时操作是否应该异步化？
- [ ] **索引**：新查询字段是否有数据库索引支撑？

---

## 维度 4：安全（最高优先级）

- [ ] **SQL 注入**：是否使用了字符串拼接 SQL？必须用参数化查询
- [ ] **XSS**：用户输入是否在输出时做了转义？
- [ ] **CSRF**：状态变更接口是否需要 token 保护？
- [ ] **权限校验**：是否校验了"当前用户能访问这条资源"？（不仅是登录态，还要鉴权）
- [ ] **敏感信息**：日志/响应里是否泄露了密码、token、密钥、身份证号？
- [ ] **路径遍历**：文件操作是否校验了路径不含 `..`？
- [ ] **反序列化**：是否反序列化了不可信数据？
- [ ] **依赖漏洞**：新引入的库是否有已知 CVE？
- [ ] **硬编码密钥**：代码里是否藏了 API key、密码？

---

## 维度 5：异常处理

- [ ] 所有可能抛异常的调用是否被妥善处理？
- [ ] 是否吞掉了异常（catch 后不打日志、不抛出）？
- [ ] 错误码 / 错误信息是否对调用方友好？
- [ ] 是否区分了"用户错误"（4xx）和"系统错误"（5xx）？
- [ ] 失败时是否会留下脏数据？（事务、回滚、幂等）
- [ ] 外部依赖（DB、HTTP、文件）失败是否有降级 / 重试策略？
- [ ] 日志级别是否合理？（error/warn/info/debug）

---

## 维度 6：测试覆盖

- [ ] 是否覆盖了正常路径？
- [ ] 是否覆盖了至少 2 个边界场景？
- [ ] 是否覆盖了异常路径？
- [ ] 测试是否独立可重复？（不依赖执行顺序、不依赖外部状态）
- [ ] mock 是否合理？（不要 mock 自己写的代码）
- [ ] 断言是否具体？（避免 `assertTrue(result != null)` 这种弱断言）
- [ ] 测试是否实际跑通？（看到绿色再说）

---

## 维度 7：风格一致性

- [ ] 命名风格是否与项目现有代码一致？（camelCase / snake_case）
- [ ] 缩进、括号、空行是否符合项目惯例？
- [ ] 文件组织是否符合项目分层？（不要在 Controller 里写业务逻辑）
- [ ] 是否引入了项目没用过的新依赖？（确认必要性）
- [ ] 注释风格是否参考了已有文件？（JavaDoc / TSDoc / docstring）

---

## 高频"必须修复"清单（Top 阻塞项）

以下问题一旦发现，**必须修复才能合并**，不要妥协：

1. SQL 注入 / XSS 漏洞
2. 敏感信息泄露（密码、token 出现在日志或响应中）
3. 未鉴权的资源访问接口
4. 数据库 N+1（用户量大时直接打挂）
5. 测试不通过 / 测试被跳过 / 没写测试
6. 把异常吞掉而不打日志
7. 硬编码密钥 / 数据库连接串
8. 改动破坏了现有测试（必须修复或更新测试）
9. 引入了未授权的新依赖

---

## Review 流程（推荐节奏）

```
1. 自 Review（主线程）
   - 跑这份清单一遍
   - 输出评分表 + Top 3
   - 立刻修复 Top 3

2. 盲审 Review（subagent，可选但推荐）
   - 派 code-improvement-scanner subagent
   - 不告诉它实现思路，只给 diff + 需求摘要
   - 对比两份 Review 的差异，关注 subagent 发现而你漏掉的点

3. 第二意见（用户操作）
   - 提示用户：建议切换到 Codex 做独立 review
   - 给出命令：codex → review git diff，重点关注 ...

4. 修复 Top 3 后，标记进入第 6 阶段（提交）
```

---

## 不要做的事

- ❌ 仅口头说"我 review 过了"，不输出评分表
- ❌ 只关注小问题（命名、格式），忽略安全/性能阻塞项
- ❌ 发现问题不修就推进到提交阶段
- ❌ 自己 review 全打 5 分（基本是没认真看）
- ❌ 把 Review 流程跳过去
