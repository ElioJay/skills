# 回滚、升级脚本与灰度

## 1. 回滚设计

回滚的目标不是"回到旧版本"，而是**在可接受的时间内把服务恢复到可接受的状态**。因此先问：这个版本失效时，最快的恢复手段是什么？选项通常不止"回滚"一种。

| 手段 | 适用 | 代价 |
|---|---|---|
| 回滚代码与配置 | 新版本引入缺陷、数据未变或可兼容 | 最快，需旧版本仍兼容当前数据 |
| 关闭开关（feature flag / 配置降级） | 新功能出问题但主体可用 | 依赖功能有开关且开关本身经过验证 |
| 前向修复（hotfix 再发一版） | 数据或结构已不可逆 | 较慢，但往往是唯一可行路径 |
| 数据修复 | 数据被写坏 | 风险最高，需单独授权与校验 |

设计时必须写清：

- **触发条件**：可观测、可判断。例如"核心接口错误率 > 1% 持续 5 分钟"或"下单成功率低于 99% 持续 10 分钟"。给出谁有权触发。
- **决策时限**：在多长时间内必须决定回滚或前向修复。没有时限的预案在现场会变成拉锯。
- **步骤与验证**：每步写操作入口、执行角色、预计耗时，以及**这一步生效的判定方式**。
- **不可回滚项**：删字段、删表、数据清洗、已对外发出的消息或文件、已推送的客户端版本。这些必须单独列出，并给出前向修复路径——它们不是回滚能覆盖的。
- **回滚后的数据一致性**：旧版本代码遇到新版本写入的数据会怎样？字段被忽略、枚举值不认识、状态机缺迁移，这些都是现场事故的常见来源。
- **验证状态**：已演练 / 未验证，二选一，不许含糊。

## 2. 升级脚本的执行顺序与幂等

顺序不是偏好问题，而是正确性问题。通用原则：

1. **先做兼容性变更**（加表、加可空列、加索引），它不破坏旧版本。
2. **再发应用**：新代码同时兼容旧结构与新结构。
3. **再做数据回填**，可分批、可中断、可续跑。
4. **最后收紧约束或删除旧结构**，通常在确认旧版本已完全下线之后。

逐项确认：

- **幂等性**：同一脚本重复执行会发生什么？报错、跳过还是产生重复数据？`CREATE TABLE IF NOT EXISTS`、`INSERT ... ON CONFLICT`、先查后插，各有各的坑。
- **中断续跑**：执行到一半失败，是从头再来还是从断点继续？重跑会不会重复处理已处理的数据？
- **顺序依赖**：哪些脚本必须在应用启动前、哪些必须在启动后？写清"必须"的依据，而不是凭印象。
- **回填的数据来源与口径**：从哪张表、哪列算出来，如何处理历史脏数据与空值。
- **前后校验**：执行后用什么查询证明结果正确（行数、抽样比对、聚合对账）。
- **锁与耗时**：大表加索引或改列可能长时间持锁。给出预计耗时与执行窗口，必要时给出在线变更方案。

**脚本正式副本属于代码仓库**，发布材料里只放执行顺序索引与说明，不要把脚本正文复制到文档里——两份副本必然漂移。

## 3. 灰度与生产验证

- **分批**：按流量比例、用户群或实例分批。每批给出进入条件与停止条件，两者都必须可判断。
- **观察指标**：至少覆盖这个版本**可能影响**的维度——核心业务指标、错误率、延迟分位、资源消耗，以及这次改动直接相关的业务计数器。只盯 CPU 会漏掉业务错误。
- **对照**：能与上一版本同时观测时，用新旧对照；不能对照时，用发布前的同口径基线。**不同口径的对比不能用来宣布发布成功。**
- **观测窗口**：时长要覆盖到一个完整业务周期（例如日结、定时任务、低峰批处理），而不是固定半小时。
- **放量决策**：写清由谁在什么条件下决定放量、暂停或回滚，以及决定前需要看到什么数据。
- **生产验证**：给出发布后必须验证的具体清单——关键路径能否走通、这次改动的目标是否达成、有没有出现预期外的日志或告警。
