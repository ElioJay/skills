# 文件定位 · Outline 提取 · 内部结构 · 依赖/消费方反查 · 选择性深读（多语言）

> 供 `code-read-deep-file` 的阶段 1~5 使用。核心前提：分析对象永远是**一个源文件**（可能含多个类/顶层函数）。
> 与方法级 `code-read-deep-function/references/tracing-rules.md` 的差异：这里是**广度优先建地图**，不是顺着一个方法深挖到底。

---

## 一、语言识别 + 文件定位（阶段 1）

### 1.1 先识别语言
按文件扩展名判定，决定 Outline 提取与依赖解析策略：

| 语言 | 扩展名 | 顶层构件关键字 | import/依赖语法 |
|------|--------|---------------|----------------|
| Java | `.java` | `class` / `interface` / `enum` / `record` | `import a.b.C;` |
| Kotlin | `.kt` | `class` / `object` / `fun`（可顶层） | `import a.b.C` |
| C# | `.cs` | `class` / `interface` / `struct` / `enum` | `using A.B;` |
| Python | `.py` | `class` / `def`（可顶层） | `import x` / `from x import y` |
| JS/TS | `.js/.ts/.tsx` | `class` / `function` / 箭头函数 / `export` | `import ... from` / `require(...)` |
| Go | `.go` | `type T struct` / `func F` / `func (r *T) M` | `import ( ... )` |

> 关键认知：**Java 一文件≈一类**，但 Python/JS/TS/Go **一个文件常含多个类与多个顶层函数**——Outline 必须把它们全列出，不能只看"主类"。

### 1.2 定位文件
1. 用户给了**相对/绝对路径** → 直接 Read。
2. 用户只给了**文件名**（如 `OrderService.java`）→ 用 **Glob** 找 `**/<文件名>`；多处命中则列出候选路径让用户选，不擅自挑。
3. Read 整个文件，记录**总行数 LOC**（写入报告「定位」）。超大文件（>~800 行）分段 Read，但仍要覆盖全文件做 Outline。

## 二、Outline 提取规则（阶段 2）—— 文件级"地图"的核心

逐行扫描文件，枚举**所有顶层构件**，构成「构成清单」表。这是本 skill 区别于方法级 skill 的关键产出。

### 2.1 要枚举的构件
- 类 / 接口 / 抽象类 / 枚举 / record / struct / trait。
- 顶层函数（Python/JS/TS/Go/Kotlin 可有）。
- 导出的常量 / 类型别名 / 配置对象（`export const`、`type X =`、Go 包级 `var/const`）。
- 类内成员：方法、重要字段（字段可汇总，不必逐个塞进 Outline，关键字段放「关键数据与状态」段）。

### 2.2 每项记录
`构件名 | kind（类/接口/函数/常量…） | 可见性（public/private/导出与否） | file:line | 一句话定位`

### 2.3 组织方式
- 有类的语言：**按"类 → 其方法"分组**列出，层次清晰。
- 无类/多顶层函数的文件：按"导出函数 / 内部函数 / 常量"分组。
- **只列不展开**：Outline 阶段只给一句话定位，不追调用链、不贴代码。大文件尤其要克制。

## 三、内部结构与协作（阶段 3）→ ① 结构图

目标：看清**文件内部各构件怎么协作**，找出"主干"。

### 3.1 方法
- 识别成员间关系：公共方法调用了哪些**私有 helper**、类之间的持有/继承/实现、内部类归属。
- 定位**主干**：对外 API 入口经由哪些内部方法实现（这条主干就是结构图的脊柱）。

### 3.2 剪枝（避免结构图爆炸）
1. **trivial 不进图**：getter/setter、`toString`/`equals`/`hashCode`、纯日志、简单 DTO 组装。
2. **第三方/标准库不展开**：本阶段只画**文件内部**结构；跨文件的依赖留给阶段 4 的依赖图。
3. **重载/同名**：图中合并表示，注明"（多重载）"。

### 3.3 产出
一张文件内部结构关系 →「内部结构与协作 › ① 结构图」（OO 用 `classDiagram`，无类语言用 `flowchart`）。

## 四、依赖反查 · 上游（阶段 4 前半）

本文件**依赖谁**：

1. 解析文件头部的 `import` / `using` / `require` / Go `import (...)`，列出所依赖的其他模块/类。
2. **区分内部依赖与第三方**：项目内文件单列（可点击 `file`），第三方/标准库标注"（第三方）"不深入。
3. **外部 IO 单列**：DB / HTTP / MQ / 缓存 / 文件 读写依赖一律标出（依赖图要用）。

---

## 五、消费方反查 · 下游（阶段 4 后半）

**谁在用本文件**：

1. 全库 **Grep** 本文件导出符号（类名/函数名/常量名）的引用点。
2. 按导入约束去重：调用方文件是否 `import` 了本文件/本类。
3. **框架反射/注解入口**：路由（`@RequestMapping`）、定时（`@Scheduled`）、监听（`@KafkaListener`）、DI 注入可能无显式调用点——按注解判断"由框架使用"并注明触发来源。
4. **测试消费方**单独标注"（测试）"，与生产消费区分。

> 产出：上游依赖 + 下游消费方 →「依赖与消费方 › ② 依赖关系图」。

## 六、选择性深读的挑选标准（阶段 5）—— 本 skill 的"深度阀门"

文件可能很大，**不能把每个方法都深挖**（那会退化成对每个方法跑一遍方法级 skill）。只挑 **1~3 个**最值得读的成员做**中等深度**详读。

### 6.1 挑选优先级
1. **用户点名**的方法（最高优先）。
2. **对外 API 入口**（消费方契约的核心）。
3. **业务主干**（承载文件主要职责的方法）。
4. **复杂度最高**（分支/循环/状态最密集，最易藏问题）。

### 6.2 "中等深度"的边界
- 讲清：这个成员的职责、关键分支/状态、它在**文件内**调用了哪些 helper、触达哪些外部 IO。
- **止于本文件**：跨方法、跨文件的**完整调用链与数据流**不在这里展开——
  一律附一句"完整调用链/数据流 → 用 `code-read-deep-function` 读 `类名.方法名`"，把深挖委派给方法级 skill。

## 七、追踪过程的取舍原则

- **宁可标注，不可假装完整**：Outline 漏列、深读省略、依赖未尽，都要在报告里显式声明边界（"（已剪枝/未逐一展开）"）。
- **广度优先**：先把全文件地图铺开，再选择性下钻；不要一头扎进某个方法回不来。
- **保持上下文连贯**：同一文件尽量在主代理内顺序读完；只有文件特别庞大时才考虑派 Explore 子代理分块读，再汇总。
- **不改代码**：全程只读不写，任何阶段都不编辑业务代码（符合仓库与全局规则）。
