# 入口解析 · 调用追踪 · 剪枝 · 上游反查（多语言）

> 供 `code-read-deep-function` 的阶段 1~3 使用。核心前提：分析对象永远是**一个方法**。

---

## 一、入口解析（阶段 1）

### 1.1 先识别语言
按项目文件与扩展名判定，决定后续解析与剪枝策略：

| 语言 | 扩展名 | 类/方法定义关键字 |
|------|--------|------------------|
| Java | `.java` | `class` / 方法签名 |
| Kotlin | `.kt` | `class` / `fun` |
| C# | `.cs` | `class` / 方法签名 |
| Python | `.py` | `class` / `def` |
| JS/TS | `.js/.ts/.tsx` | `class` / `function` / 箭头函数 / `export` |
| Go | `.go` | `func (r *T) M(...)` / `func F(...)` |

### 1.2 定位入口方法
1. 用 **Glob** 找到候选文件：按类名找 `**/<类名>.*`，或按命名约定（Java 类名=文件名）。
2. 用 **Grep** 在文件内定位方法定义行，拿到 `file:line` 与完整签名。
   - Java/C#：搜 `<返回类型> <方法名>(` 或 `<方法名>(`。
   - Python：搜 `def <方法名>(`。
   - JS/TS：搜 `<方法名>(` / `<方法名> =` / `<方法名>:`。
   - Go：搜 `func .*<方法名>(`。
3. 用 **Read** 读取方法体（含必要的上下文行）。

### 1.3 消歧（多命中必须问用户）
出现以下情况时，**列出候选（含包名 + 完整签名 + file:line）让用户选**，不擅自挑：
- **同名类**：多个包/目录存在同名类。
- **方法重载**：同名方法多个签名（参数不同）。
- **同名函数**：不同模块/文件存在同名顶层函数。

> 消歧结果写入报告「定位 › 消歧说明」。

## 二、下游调用链追踪（阶段 2）

### 2.1 方法
从入口方法体出发，逐条识别它发起的调用（方法调用、构造、静态调用），对每个**保留**的被调方递归 Read 其定义，继续向下，直到命中剪枝边界。

### 2.2 剪枝规则（必须执行，否则指数膨胀）
1. **最大深度**：默认向下 **3~5 层**；超出则停止并标注「（已剪枝，超出深度）」。深度可由用户调整。
2. **跳过标准库与第三方**：不进入语言标准库与依赖目录——
   - JS/TS：`node_modules`；Python：`site-packages` / 标准库；Java/Kotlin：JDK（`java.*`/`javax.*`）与 Maven/Gradle 依赖；Go：标准库与 `vendor` / module cache；C#：BCL 与 NuGet 包。
   - 命中第三方调用时，把它作为**叶子节点**标注（如 `okhttp.Call.execute()（第三方）`），不展开。
3. **跳过 trivial 调用**：getter/setter、`toString`/`equals`/`hashCode`、纯日志（`log.info` 等）、简单 DTO 组装——不作为节点展开（除非它就是问题所在）。
4. **接口 → 实现**：遇到接口/抽象方法调用，定位其实现类（Grep `implements <接口>` / `: <接口>` / 同名方法）；实现唯一则跟进，多实现则在图中标注分叉并挑主路径，注明其余实现「（多实现，未逐一展开）」。
5. **递归环检测**：维护「已访问方法集合」（按 `类.方法+签名` 唯一标识）；再次遇到已访问节点时，画一条回边并标注「（递归/环，已切断）」，不重复展开。
6. **外部 IO 必标**：DB / HTTP / MQ / 缓存 / 文件 读写一律作为特殊叶子节点保留并标注（数据流分析要用）。

### 2.3 产出
一棵下游调用树 →「流程 › 逻辑调用图」与「上下游 › 下游」。

## 三、上游消费方反查（阶段 3）

### 3.1 方法
全库 **Grep** 入口方法名的调用点，再按语言特征去掉同名误报：
- 加类型/接收者约束：`<变量/类型>.<方法名>(`。
- 结合导入/包路径过滤：调用方文件是否 import/引用了入口所在类型。
- 注意接口调用：上游可能通过**接口类型**调用到本实现，反查接口方法名 + 实现绑定。

### 3.2 注意点
- **框架反射/注解入口**：Controller 路由、定时任务、MQ 监听、DI 注入的调用可能没有显式调用点——根据注解（如 `@RequestMapping`/`@Scheduled`/`@KafkaListener`）判断「由框架调用」，并在上游里注明触发来源。
- **测试调用**：上游若来自测试代码，单独标注「（测试）」，与生产调用区分。

### 3.3 产出
上游调用方列表 →「上下游 › 上游」与上下游关系图左侧。

## 四、追踪过程的取舍原则

- **宁可标注，不可假装完整**：任何省略都要在报告里显式声明边界。
- **主路径优先**：分支太多时，沿最主要的业务路径深入，旁支浅尝即止并标注。
- **保持上下文连贯**：同一条链路尽量在主代理内顺序读完；只有链路特别庞大时才考虑派 Explore 子代理分支并行，再汇总。
- **不改代码**：追踪只读不写，任何阶段都不编辑业务代码。
